#### (2) ★★ 真 bug：地雷/定時炸彈的占用判据被读成 **8 槽**，原版是 **4 字节**

原版两支在监狱/医院格上是：

```asm
00421446  mov  dx, word ptr [0x48bae0]   ; 监狱节点 id
0042144d  cmp  eax, edx / jne …
00421451  cmp  dword ptr [0x496b30], 0   ; ★ 一次比 **4 个字节**
00421458  jne  0x42147d                   ;   → 直选该格
```

`cmp dword [0x496b30], 0` 只覆盖 **槽 0..3（= 玩家）**。而复刻的
`ai/tool-policy.ts` 的 `mineLike` 用的是 `anyoneConfined`（**逐槽扫 8 个**，含 4..7 物件槽）
⇒ **只要某个物件槽非 0，AI 就会把地雷/定時炸彈直接埋在监狱/医院格上**，而原版这时
只会把它当普通格处理。

这正是 **§四之二 第 3 条**在「落点 8 槽 / 新闻 4 字节」上修过的**同一个宽度区分**，
当时把新闻改成了 `anyPlayerConfined`，**漏了道具 AI 这第三处**。

**修法**：`mineLike` 的两处改 `anyPlayerConfined`（`anyoneConfined` 那把「逐槽 8 个」的
注释也一并订正为「仅落点用」）。

**验证（可证伪）**：差分 [E]/[F] 两组共 12 例专钉这条，含「仅物件槽 4 / 7 被占 ⇒ 不直选」
「仅物件槽被占 + 监狱格是空格 ⇒ 完全无候选（8 槽口径会误直选）」。
TS 侧新增 **3 例**（`ai/tool-policy.test.ts` 的「3 地雷」块）；实测把两处退回
`anyoneConfined` 后这 3 例**立刻红**，恢复后 55/55 绿。

#### (3) 本条踩到的四个**测试自己**的坑（都记下来，免得重踩）

1. **绝对地址 vs 指针**：物件表是 `mov al, byte [eax*8 + 0x496d08]` ——
   `0x496d08` 是**绝对基址**（.bss 里的数组），**不是指针**。我起初把它当指针
   （写到 `SCRATCH_BASE+0xA000` 再让代码读 `[0x496d08]`）⇒ 恒读到 0。
2. **物件下标 0 基**：`dec ebp` 在查表之前 ⇒ 写测试数据要用 `(idx-1)*0x18`。
3. **桩的返回值语义各不相同**：前瞻/反瞻返回「是否岔路」，而可见表填充
   （`0x409ef9`/`0x40a45c`）返回的是**项数** —— 共用一个「返回槽」会让后者恒为 0
   （表现是「可见表明明铺了，候选却是空」）。
4. **暂存区地址别和表撞**：路径源区一开始取在 `NODES+0x2000`，正好落在
   `LANDS`（`SCRATCH_BASE+0x3000`）上 ⇒ 铺地块表把路径覆盖掉。
   **桩用的源区要和所有表错开**。

> ★ 这四条的共同点：**现象都像"被测函数读错了"，实际都是测试台自己的问题**。
> 与第 154 条（`hated` 恒 −1）同族 —— 「先怀疑测试，再怀疑被测」这句话要在**第一步**执行。
