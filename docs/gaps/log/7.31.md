### 7.31 ★ 第 50 条（本轮）：两处「会悄悄分叉」的收口 —— 加持门槛与状态指纹

两件都是「同一个道理写了两份 / 该进指纹的没进」这一类：**不改玩法数值，
但都会在将来某次改动里悄悄分叉**。

#### (1) 神明加持：门槛只留一份，并删掉那个会把 bug 请回来的 API

第 37 条修过「无条件多掷一次随机数」，但修法留了个尾巴：
`rules/blessing.ts` 的 `playerBlessingMultiplier(p, coinFlip, kind)` 要求调用方
**先算好 `coinFlip`** —— 而「先算」就意味着**无条件掷一次**，正是那个 bug 的形状；
`reduce.ts` 于是绕开它、自己写了一小段门槛（`> 50 && <= 100`），
**门槛就成了两份**。

现在换成唯一入口：

```ts
blessingLevelWithDraw(p, kind, draw): number   // draw 只在中间档被调用一次
```

`reduce.ts` 改为 `blessingLevelWithDraw(me, blessKind, () => rng.next() & 1)`，
重复门槛删除，`playerBlessingMultiplier` **删掉**（死 API，只有测试在调）。

`rules/blessing.test.ts` 17 → **21 例**，新增一组专测「`draw` 到底被调了几次」：
`> 100` 掷 0 次、`恰好 100` 掷 1 次、`51..99` 掷 1 次且用掷出的那一位、
`恰好 50 / 0..50 / 负值` 都是 0 次；三种用法的中间档各掷一次，
且**罚金/劫难的档位是反的**（reward 掷出 1 → 档 2；penalty/misfortune → 档 1）。

#### (2) `stateFingerprint`：补上漏掉的**规则相位**，并分两种口径

★ 先说一个**真缺陷**：`pending`（待决交互）、`pendingNpcSlots`（惡人段游标）、
`pendingQueue`（排队的拍卖）**都不在指纹里**。`state/types.ts` 上早就写着
`pendingNpcSlots`「要进指纹」，实现里一直没有。后果：**两端一个挂着「買地」、
另一个已经答完，校验和照样相等** —— 而这正是校验和该抓的东西。

现已补入，并用**规范化 JSON**（键排序、数组保序）序列化 `pending`/`pendingQueue`
—— 不能直接 `JSON.stringify`（C-DET-5 禁依赖 `Object.keys` 顺序），
`canonicalJson` 恰好是**排序后再用**，故带定向豁免。

★ 再说口径：加第二参 `{ rng: false }`：

| 口径 | 用途 | `rngState` |
|---|---|---|
| 默认 | **复刻↔复刻（联机）** | **要**（规则性一致，是 desync 的早期信号） |
| `{ rng: false }` | **复刻↔原版（通道 3 轨迹差分）** | **不要** —— 原版 PRNG 被表现层共用（台词 5 处 + 拍卖窗口动画 4 处按帧），无头引擎不可能逐位对齐，带着它比对只会一直报**假失步** |

安放位置已核过：校验和是**按 `seq`** 比对的（客户端在施加第 seq 条 action 之后
上报、服务器查 `fingerprintAt(seq)`）⇒ 两端比的是**同一个动作位置**，
把 `pending` 这类规则状态加进去**不会**造成假失步。

`net.test.ts` 16 → **19 例**：三项规则相位各自参与指纹；**键序不敏感**
（两组插入顺序不同的同一对象 → 同指纹）而**数组顺序仍然敏感**；
`{ rng: false }` 忽略 `rngState` 但**照抓**玩家现金与 `pending` 的分歧。

#### 诚实边界

- `canonicalJson` 对 `undefined` 按 JSON 惯例**丢弃**（对象里）／保留字面量
  （数组里）—— 指纹只用于比对，不用于重建，故这一处理足够。
- 指纹**仍未覆盖**地图块本身（节点/装饰）与 `objects` 之外的渲染量 ——
  这是有意的：地图在同局内不变，而它一变就是换图，不是 desync。
