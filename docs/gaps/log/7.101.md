### 7.101 ★ 第 118 条（本轮）：落点分派器主段 `0x4198b9` 的**取证完成一半** —— 格值是 **1 基**、边界逐字节核对；测试稿留在 `scratch_*`（未进闸门）

第 117 条把 `0x4198b9` 的地块两支与复刻对读完毕（结论：一致）。
本轮想把它们**机器驱动**起来（工作单要的就是 A 级证据），进展与卡点如下。

#### (1) ✅ 解掉的两件事

**① 格值是 1 基**：`(v − 0x7d0) × 0x34` 要落在第 `id` 条记录上 ⇒ `v = 2001 + id`。
写 `v = 2000 + id` 会**整体偏移一条**，而 `v == 2000` 那一格正好落进
`0x41a168` 那一支 —— 这就是上一轮「明明设了地产格却走进了設施支」的根因。

**② 两条边界与跳转逐字节核对过**（不靠助记符）：

```asm
004198c9  66 81 fb d0 07     cmp  bx, 0x7d0
004198ce  0f 86 94 08 00 00  jbe  0x41a168      ; ★ 0x7d0 = 2000（含等号）
004198d4  66 81 fb a0 0f     cmp  bx, 0xfa0
004198d9  0f 83 89 08 00 00  jae  0x41a168      ; ★ 0xfa0 = 4000（含等号）
```

⇒ **地块格的格值域是 `2001..3999`**；`2000` 与 `4000` 都归 `0x41a168` 那一支
（`game-loop.md` 写的「2001..3999」因此得到机器级确认）。
另外 `0x4198c3` 的 `0f 84 → 0x41b3d0`（尾声）也核过（`bx == 0` 才走）。

#### (2) ❌ 卡点（如实登记）

改成 1 基之后**确实弹出了框**，但 `sprintf` 入口的 hook 显示：

```
ebx=0x7d1（格值 2001 ✓）  ebp=0x0
args = [buf@0x53ff00, **0x4639e1**, 0x601038, 0x0]
记录 dump: owner=1 level=2 type=0 house=100   地块表基址 = 0x601000 ✓
```

① 格式串是 `0x4639e1`（**买地**那条 `%s\n\n費用:%d元\n\n是否買下此地？`），
而 `owner == 1` 按原版逻辑该走**升级**（`0x46396d`）；
② 第三个实参 `0x601038` 是记录里的**名字指针**（`esi+4`），不是费用。

⇒ 最可能是**这个 `sprintf` 不是 `0x419967` 那一处**、执行流先进了别的分支。
下一轮第一步：hook 记录 `0x419967` 到底有没有被执行，再决定这条驱动路径是否可用。
