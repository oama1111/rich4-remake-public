#### (2) ★ 逮到工具一处**区间过宽**：`0x497158` 一族被算成「全局资金/回合」

`IMPACT_REGIONS` 原来写 `(0x499078, 0x499120)`，而 `0x497158..0x497165` 落在
**另一个区**里却与它相邻 —— 那些字节是 **`RICH4.CFG` 的设置**：

```asm
; @source 0x00411e8f（本轮读通）—— RICH4.CFG 读写器
00411e93  push "rb" / push "RICH4.CFG" / call 0x4573bf   ; fopen
00411eae  push 0x10 / push 0x497158 / fread              ; ★ 16 字节设置
00411ec2  push 0x38 / push 0x497168 / fread              ; ★ 56 字节热键/控件表
00411eda  （文件不在）mov byte [0x497158],1 … memcpy(0x497168, 0x47edc2, 0x38)
```

⇒ 它**只动设置字节，一个规则态都不碰**；`0x497158` 就是 `tick.ts` 里那个
`game speed`（`cfg[0]`）。本轮把区间收窄成 `(0x499080, 0x499120)`（公库/物价/
当前玩家/人数/牌堆/回合），并给工具加了 `VERIFIED_NOT_RULE` **手工白名单**：

| VA | 结论 | 判据 |
|---|---|---|
| `0x411e8f` | RICH4.CFG 配置读写（非规则）| 读写全是 `0x497158` 一族设置字节 |
| `0x40b8d8` | 图素资源释放（表现）| `my_free` + 清 `0x498eb4 + n*0x34 + k*8 + j*4` 四张图素 |
| `0x40c03b` | 批量清图素（表现）| 对槽 0..8 各调一次 `0x40b8d8(槽,0)` 与 `(槽,1)` |

#### (3) ★ 顺带订正 §7.94 的「`0x40829d` 不写规则字段」

§7.94 的结论是「它重画棋盘、不动规则状态」，**方向对、口径要补**：
本轮实测（`eval_block(0x40829d, 0x4083a4)` + 桩掉 `0x40aa0f`）它在
**「当前玩家编号 ≥ 4 且 `[0x48b2ac] == [0x48b2b0] == 0`」**那条路上会写：

| 写点 | 写什么 |
|---|---|
| `0x4082fb` | `player[当前].+0x0c(nodeId) = 当前空闲节点数`（那条路上为 **0**）|
| `0x408340` | `player[当前].+0x0e(lastNodeId) = 邻居槽里 `rand()%k` 摇一个` |
| `0x40836f` | `player[当前].+0x10(facing) = dir(旧节点 → 新节点)`（`0x407a8c`）|

⇒ 它是**「相机收到非法位置时把当前玩家摆回一个空闲格」**的兜底路径
（`0x40aa0f` 才是真正挑空闲格的那一支，`0x40829d` 用的是它的返回值当节点号），
**正常游玩不可达**（要求 `[0x48b2ac]`/`[0x48b2b0]` 两个相机参数都为 0）。
故 §7.94 的「不是存盘写入器、不是通用规则函数」**维持**；
但「一个规则字段都不写」这句话按上表订正 —— 它写的是**位置的兜底修复**。

#### (5) ★ 顺带读通**投注屏窗口过程** `0x42f7fc` 的消息表（为下一轮差分铺路）

按工作单现在的排序，`0x42f7fc`（1,230 字节）已经是**影响面第一**（26 分，
9 个规则写点）。本轮先把它的入口分派读清楚（`cmp eax, …` 链）：

| 消息 | 去向 | 干什么 |
|---|---|---|
| `0x401` | `0x42f885` | `WM_USER+1` 建屏：`SetTimer(hwnd, [0x46cad8], 0x64, 0)` ⇒ **100 ms** 定时器；`[0x48c372] = 0` |
| `0x405` | `0x42f930` | `WM_USER+5`：**状态置位**（`[0x48c370] = wParam`）|
| `0x406` | `0x42f94f` | 收屏那一步（画图 2 + 「拜拜」气泡，`[0x48c370] = 5`）|
| `0x113` | `0x42fa2f` | `WM_TIMER` —— 状态机主体 |
| `0x201` | `0x42fe8c` | `WM_LBUTTONDOWN`：判号格（按下即买）|
| `0x205` | `0x43003d` | `WM_RBUTTONUP`：走人（`play_sound_effect` + `PostMessage(0x406,5,0)`）|
| `0xf` | `0x430062` | `WM_PAINT` |
| `0x203` | `0x42fe8c` | `WM_LBUTTONDBLCLK` 与按下同路 |

`WM_TIMER` 那一段的三道闸（`0x42fa2f`）：
`[0x48c370] != 0` → `[0x46cb01] != 0`（本帧该不该走一次 tick）→
`[0x48c36c] == [0x46cad8]`（**定时器 id 就是建屏那一刻的 `[0x46cad8]`**，
`0x0042f8b0`），过了才 `0x44ee18(气泡下标)` 推进；随后
`jmp [([0x48c370]−1)*4 + 0x42f7e8]`（状态 1..5 的五路跳表）。
⇒ 状态推进**由 `WM_TIMER` 驱动**，而该窗口过程的 `tick` 数**不随游戏速度分频**。

⚠️ **由此得到一条待验证的口径**：本引擎的整屏计时用的是 `env.now`
（`performance.now()`，见 `ui-screen.ts` 的 `UiScreenEnv.now`），而原版这个屏
的节拍来自 `SetTimer(…, 0x64)`。两者在默认速度下按同一节拍（`0x64` = 100 ms
与 `LOT_TICK_MS = 100` 一致），但**游戏速度档会不会改变 `SetTimer` 的实测间隔
尚未验证** —— 已验证的只有「定时器 id 取 `[0x46cad8]`」这一条。
下一轮要做的：① 用 `eval_block(0x42f7fc, 0x4300f0)` 驱动消息序列，
把 `[0x48c370]` 的状态链与 `[0x44ee18]` 的气泡下标逐条钉住；
② 再判「速度档是否影响本屏节拍」。
