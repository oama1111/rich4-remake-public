### 7.30 ★ 第 49 条（本轮）：读原版存档后**時光機不再是空转** —— 快照读入侧

簇 B 的最后一个玩家可观察缺项。`savegame.ts` 先前硬写
`snapshots: [null, null, null, null]` —— 读档后按時光機相当于没存过快照
（`restoreSnapshot` 返回 `null` ⇒ 连道具都不消耗）。

#### 做法：不另写字段映射，走**写出器的逐字节逆运算**

快照不是另一种格式，而是**状态块的一个子集**：`SNAPSHOT_REGIONS` 那 28 个区
（9,999 字节）与状态块同源同义，只是落点偏移不同。所以读入就是：

```text
合成状态块 = 当前状态块 ⊕ 快照的 28 个区（按 SNAPSHOT_REGIONS 搬回状态块偏移）
合成存档   = 合成状态块 + **该快照自己的地图副本**
⇒ 交给现成的 parseSave → importOriginalSave
```

两条要点：
1. **必须用快照自带的地图副本**去解析（回合开始时的归属/等级就在那份地图里），
   否则「状态是回合开始的、归属是现在的」；
2. **空槽靠有效标记判**（快照 `+0x0000`，`@source 0x004480ce` 只给真人写 1）
   ⇒ 没存过就保持 `null`，与「時光機没快照时不消耗道具」一致。

新增 `importOriginalSaveWithSnapshots(raw, fallbackMap)`（`importOriginalSave` 的完整版），
客户端 `importOriginalSaveFile` 换用它。

#### 验证（含**独立交叉验证**）

`loaders/save-writer.test.ts` 34 → **38 例**：

1. **两个真实存档互补**（所以断言都不空）：
   - `Save0.dat` → 槽 **0/1** 有快照（两名人类玩家）、2/3 为空；
   - `SAVE1.DAT` → **四槽全空**（有效标记全 0）⇒ 读入器**不会凭空造快照**；
   - 逐槽断言「`snapshots[i] === null` ⟺ 文件里那一槽的有效标记为 0」。
2. ★★ **独立交叉验证**：把还原出来的日期与**快照字节自己**的日期
   （快照 `+0x0004`）比对 —— 不依赖任何复刻侧的中间结论。
   实测 Save0 的两槽都是 **2002-10-22**，而当前局面是 **2002-10-23**
   （快照 = 回合开始时，早一天），两边吻合。
3. ★ **往返**：`writeOriginalSaveFile({snapshots: [bent0, null, bent2, null]})`
   写出去再 `importOriginalSaveWithSnapshots` 读回来 ——
   掰过的日期与现金**原样回来**，`null` 槽回来还是 `null`。

**反证**：把读入侧强制返回 `null`（退回旧行为）⇒ 上述 3 条立刻红。

#### 诚实边界

- **只读「快照里的状态块子集」**：快照自带地图副本用于解析，
  但那份地图**没有存进快照 JSON**（`GameState` 里没有地图的历史副本），
  所以回滚后地图归属来自 JSON 里的 `landOwner` 等数组 ✓（那些确实被还原了），
  而「地图文件本身」（节点/装饰）不参与回滚 —— 与原版一致（原版也只回滚加载数组）。
- **未验证「游戏内实际按下時光機」的表现层路径**：本轮只保证 core 的快照可用
  与内容正确；界面按钮走的是既有的 `restoreSnapshot` 那条路。
