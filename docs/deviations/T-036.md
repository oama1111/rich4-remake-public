## 二、有意偏离

### ~~D-036-1 中奖号只能从 `before → after` 反推~~（**2026-09-23 已消除**）

号码由 core 在开奖那一刻交出（`GameState.lastLotteryDraw`，纯表现提示、只活一条 action、
不进指纹/存档），`lotteryDrawCue` 只读它；「没人中奖时当 0 号播」的近似随之删除。

### D-036-2（近似）脸的「眨眼」改成按帧号推

原版是 `rand() >> 9` 抽（0x00431117 起）：落 0 / 1 / 2-3 / 4-5 时分别启动
槽 1/2/3/4，其余 58/64 不动。本模块用**同一个 `hash32`**（与 core 的
`facePartsAt` 同源）按帧号推 —— 不是改良：动画不该消耗游戏随机流（C-DET-1），
而且原版每天 `srand(GetTickCount())`，那串数本来就不可复现。
**每个槽的触发概率与帧表都逐个照抄**（1/64、1/64、2/64、2/64；
表 `0x00475660` → 槽 2 = `8,7,8,10`、槽 3 = `16,17,16,15`、槽 4 = `9,10`、槽 5 = `14,15`）。

★ 顺带订正了 core 注释里的一处**对调**：低 4 位的槽号与帧表下标是**错开 3 个字节**的
（槽 2 读表 +3、槽 3 读 +7、槽 4 读 +10、槽 5 读 +12），不是「槽 1 读第一个表」。

### D-036-3（未解出）脸的推进周期

原版脸的推进挂在**同一条 50 ms 定时器**上（`0x00431431` 是定时器分支的尾巴），
但嘴的倒数器 `[0x48c34c]` 取的是 `rand() & 0xf`（0..15 拍 = 0..750 ms），
而槽的帧表只有 2/4 帧 —— 两种节拍对不上，怀疑原版另有更快的节拍源
（例如 `fcn_00450f04` 那一套，它自己在 `timeGetTime` 上转）。
本模块**按 50 ms 一拍**推进（与状态机同拍），差异只影响眨眼看起来的快慢。

### ~~D-036-4（有意）字框寿命固定 2 秒~~ —— 2026-09-23 已按原版收口（第十三份試玩回報）

原版 `fcn_0044ee18(0)`：满 2 秒（`[0x4762c4]` 的 `timeGetTime` 差 ≥ 0x7d0）**且**
音效档开着时语音不在响（`0x0044ee6c call 0x4544b9`）才算收掉 ⇒ 字框挂 **max(2 s, 语音时长)**。
现在由 `voice-sink.ts` 的 `voiceBusy()` 回答「还在响吗」（魔法屋先接上的那条出口），见 `Active.bubbleDown`。

同一轮修掉的**真 bug**：`bubbleLines` 在绘制链里**每帧**顺手播 `#NNNN`，`main.ts` 的去抖只挡
「还在响 / 500 ms 内」⇒ 短于 2 秒的句子一播完就被重起（`#0034`/`#0035`/`#0019`/`#0032` 两遍、
`#0036「行動要快喔！」` 三遍）；长于 2 秒的（`#0017`/`#0018`/`#0033`）则在 2 秒被下一句叠上。
现在语音只在进步那一拍（`enterStep`）请求一次，绘制链只剥不播。

### D-036-5（有意）`Data.mkf` #517 的人像条

各人持号表里那一排 189×116 的**人像条**在 `Data.mkf` 资源 **517**
（@source 0x0040808f `push 0x205`），四张分别是四个座位。
本屏照画；`Data.mkf` 已在 `ArchiveName` 里，故不需要新出口。

### D-036-6（**本轮新增 · 近似**）铭牌底框的「压暗」用 canvas 半透明黑重画

每个玩家画持号表之前，原版先调 `fcn_004552e7(surface, 铭牌.x, 铭牌.y, 0x128, 0x3c, -16)`
（@source 0x0042f482 起）—— 那是**换色表**操作（`[0x485d68] + (−16 << 5)`，
一张 256 色 × 2 字节的表），效果是**5 位分量减半**，也就是屏上看见的「四个蓝框」。
本引擎每帧整屏重画，做不到就地改像素，所以按同值观感重画一遍：
`rgba(0,0,0,16/32)` 的 296×60 矩形（`TALLY_FRAME`，与 `board-screen.ts` 的
`PRESS_ALPHA`、`options-pages.ts` 的 `HOTKEY_PRESS.edgeAlpha` 同一族做法）。

★ 上一版**整个没画这一块**（`drawTally` 只画人像条 + 徽章 + 数字牌），
所以「四个蓝框」是空的 —— 这是本轮修掉的第 1 条。

### D-036-7（**本轮新增 · 有意偏离**）号码表用**开奖前**那一份，不是 `state.lottery`

原版在**最后一步（状态 10）**才 `memset(0x4990b8, 0, 0x24)`（@source 0x00430ab5
一带，紧接派彩），所以整场演出里铭牌上一直看得见各人的号码。
而本引擎的 core 在**开奖那一次 action 里**就把表清掉了
（`places/lottery.ts` 返回 `emptyLottery()`，`reduce.ts` 同一次写回）——
拿 `state.lottery` 去画就是**四块空铭牌**（这就是「中奖反而看不到号码」的根因）。

本模块**不改 core**（C-ARC-2），改成在 `DrawCue` 里留一份**开奖前**的号码表
（`cue.sold = [...before.lottery]`），屏上用它。屏上效果与原版一致；
差异只在「core 里的表什么时候清」—— 那一条要中央决定是否搬进状态机。

## 三、核过的三处「卡片标注未实机核对」

卡片 note 里点名要回 exe 再核的三处，结论都在上面：

1. **状态 6/8 的擦除矩形** —— 见上表第 3/5 条：状态 5 是两块
   `(0,150)-(419,271)` / `(150,270)-(301,361)`，状态 8 是
   `(472,116)-(517,206)` + 左脸 `(52,89)+46×40`。**已逐条对上**。
   （卡片正文把这两步的状态号写成了 6/8，实际是 **5/8** —— 状态 6 只说话不擦。）
   ★ 顺带核出：端点全是**开区间**（宽度 = `x1 − dx`）—— 见上表后面那条注。
2. **脸部动画几帧** —— 见 D-036-2：帧表已逐字节对上（`0x00475660`）；
   只差**推进周期**（D-036-3）。
3. **ANM 只实装 `flags bit0=1`** —— 本屏用到的两条都不需要它：
   摇球 `flags = 8`（@source 0x0043037a）、礼花 `flags = 1`。
   ★ 顺带核出一件更要紧的事：**帧间隔不是 FLIC 头里的 71 ms** ——
   原版把它读进 `[0x48c870]` 之后**从来不读**，真正用的是
   `[0x48c864]`，没给 `flags` 时取 **0x370 = 880 ms**
   （@source 0x00450e9c / 0x00450eb1）。于是摇球 42 帧 ≈ 37 秒、
   礼花 37 帧 ≈ 33 秒 —— 这正是「状态 5 那条判据会卡那么久」的由来。
   本屏按 880 ms 走（`ANM_FRAME_MS`）。

## 四、还没做的

- **ANM 只在 `draw` 里逐帧贴**，没有原版那种「rgb555 帧 + 调色板轮换」的
  自绘路径（`fcn_00456b3e`）—— 解码器给的就是 RGBA 位图，视觉一致。
- **原版的「点击跳过」**（`flags & 2`，0x004514fd 那一支）本屏没有 ——
  ★ 这**不是缺口**：本屏那两处 ANM 的 `flags` 分别是 **8**（摇球，`loc_0043036c`）
  与 **1**（礼花，`loc_00430485`），bit1 都是 0，**原版这一段本来也跳不过**
  （只有 `flags & 2` 才把 `[0x48c880]` 挂上跳过闸）。
