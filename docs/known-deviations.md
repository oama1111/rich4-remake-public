> 本文件登记**所有**有意偏离，每条必须说明理由。凡未登记的差异一律视为 bug。

## D-001：随机数播种策略按模式区分

| | |
|---|---|
| **类别** | **单机：零偏离**（完整复刻原版）｜**联机：新增行为**（原版无联机，无对应物可偏离） |
| **影响** | 不影响任何概率分布 |
| **状态** | 已实施（`packages/core/src/rng/policy.ts`） |

> **修订记录（2026-09-13）**：本条最初的方案是「全局改为显式注入种子」，那会让单机
> 失去原版的"读档重开刷结果"。经复核，这是把**引擎确定性**与**存档策略**两件事
> 混为一谈了。拆开后两者可以同时满足，单机的偏离**完全消除**。见下方「最终方案」。

### 原版行为

原版全程序共 **3 处** `srand()` 调用，**全部**以 `GetTickCount()`（系统启动至今的毫秒数）为种子：

| 地址 | 位置 | 时机 |
|---|---|---|
| `0x0040170F` | `asm/rich4_initialize.asm:146` | 游戏启动，DirectDraw 初始化后 |
| `0x00402FA1` | `asm/rich4_save_files.asm:507` | **读档之后** |
| `0x0041D06E` | `asm/rich4_player_core_actions.asm:4830` | 回合/新一天推进时 |

因此：
- 原版存档**不保存 PRNG 状态**；读档后重新播种，所以"读档重开会刷出不同结果"是**原版的真实行为**。
- 每回合都会用挂钟重新播种，PRNG 序列在回合之间被打断。
- **原版对局本质上不可复现。**

### 最终方案

关键是把两件**本不相干**的事拆开：

| 关注点 | 要求 | 由谁决定 |
|---|---|---|
| **引擎确定性** | `reduce(state, action) → state` 必须是纯函数 | 引擎本身，两种模式**都成立** |
| **存档是否写入 PRNG 状态** | 决定能否"读档刷结果" | 存档**策略**，按模式取不同值 |

做法是把「重新播种」表达为 action 流中的**一条显式 action**，而非让引擎去读挂钟。
非确定性因此被捕获成 action 日志里的**数据**，引擎保持纯函数。

| | 单机 `SINGLE_PLAYER_POLICY` | 联机 `MULTIPLAYER_POLICY` |
|---|---|---|
| PRNG 算法 | 位级一致 | 位级一致 |
| 存档写入 PRNG 状态 | **否** | 是 |
| 重新播种时机 | 启动 / **读档后** / **每回合**（与原版三处 `srand` 逐点一致） | 仅开局一次 |
| 读档重开刷结果 | **可以**（原版行为） | 不适用 —— 联机没有"读档"这个动作 |
| 断线重连 | 不适用 | 服务器下发含 PRNG 状态的完整快照，属**重同步**而非读档 |

### 为什么单机算「零偏离」

单机模式下，播种时机与原版三处 `srand(GetTickCount())` **逐点对应**，存档同样不含
PRNG 状态，因此「读档重开刷结果」这一原版特性被**完整保留**。玩家可观测的行为与原版
没有任何差异，故不构成偏离。

### 为什么联机算「新增」而非「偏离」

原版**没有联机模式**，不存在可供偏离的原版行为。联机的确定性播种是全新设计，
用于满足 DEVELOPMENT_PLAN.md §5.2 **C-DET-4**（断线重连、反作弊、赛后回放）。
它不改变任何一条游戏规则或概率分布。

### 附带收益

因为 reseed 值被记入 action 日志，**单机局同样可以完整回放**——
调试、复盘、bug 复现都能用，而这是原版做不到的。

### 溯源

- 原版 PRNG：`Rich4/rich4.exe` VA `0x00456F2D`（反汇编原始二进制确认）
- 原版三处 `srand`：`0x0040170F`（启动）、`0x00402FA1`（读档后）、`0x0041D06E`（回合推进）
- 实现：`packages/core/src/rng/watcom.ts`、`packages/core/src/rng/policy.ts`
- 测试：`packages/core/src/rng/watcom.test.ts`、`packages/core/src/rng/policy.test.ts`
  （其中「读档重开能刷出不同结果」与「重连恢复后结果完全一致」各有专门用例）

## ⚠️ 陷阱记录（非偏离，但必须避免）

### T-001：不要沿用 rich4-re 的 `mscrt.ld` 随机数映射

`rich4-re/asm/mscrt.ld:15-16` 把原版的 CRT 随机数重定向到了 msvcrt：

```
PROVIDE(_libc_srand = _srand);
PROVIDE(_libc_rand  = _rand);
```

msvcrt 的 `rand()` 用的是乘数 `0x343FD`、增量 `0x269EC3`，与原版 Watcom 的
`0x41C64E6D` / `0x3039` **完全不同**。

**后果**：逆向项目构建出的 `rich4_mscrt.exe` 虽然能运行，但**随机序列已与原版不同**。
任何从该可执行文件观测到的随机行为都不可作为保真依据。

正确做法是以**原始 `rich4.exe` 的反汇编**为准，本项目已如此实施。

## 已查明的原版机制（非偏离，存档实证）

### F-001：开局资金分配

| 项 | 值 | 证据 |
|---|---|---|
| 初始资金 `_rich4_game_initial_fund` | **300,000** | `Save0.dat` 与 `SAVE1.DAT` 偏移 `0x268A` 均为 300000 |
| 开局现金 | `初始资金 × init_cash_ratio / 100` | 见下表 |
| 开局存款 | `初始资金 − 开局现金` | 同上 |

`SAVE1.DAT` 是一局刚开始的游戏，四名玩家的现金/存款拆分**精确匹配**各自角色的
`init_cash_ratio`（该字段来自 `rich4_characters.c`）：

| 玩家 | 角色 | 现金 / 存款 | 现金占比 | 角色的 `init_cash_ratio` |
|---|---|---|---|---|
| 1 | 孫小美 | 150,000 / 150,000 | 50% | **50** ✓ |
| 2 | 阿土伯 | 120,000 / 180,000 | 40% | **40** ✓ |
| 3 | 金貝貝 | 240,000 / 60,000 | 80% | **80** ✓ |
| 0 | 小丹尼 | 150,000 / 150,000 | 50% | 55（见下） |

玩家 0 是该存档的当前行动玩家，已经行动过；按 55% 开局应为 165,000 / 135,000，
现为 150,000 / 150,000，差额恰为一笔 15,000 的银行存入。故不构成反例。

> 这同时解答了 M1 阶段留下的疑问（「小丹尼 ratio=55 却是 50:50」）。

### F-002：物价指数的更新时机与公式（原 Q17，已结案）

**公式**（`rich4_update_price_index.asm`）：
```
新指数 = (在场玩家总资产之和 ÷ 在场人数) ÷ 初始资金      // 两次均为 idiv，向零取整
if (新指数 > 当前指数) 当前指数 = 新指数                  // 只升不降
```
「在场」的判据是 `cmp byte [player+0x15], 0`，即 **who_plays 整个字节非 0**。

**调用时机**：全程序**仅一处**调用，位于日期推进函数 `fcn_0041cf67`
（`rich4_player_core_actions.asm:4761`），即**每推进一天**更新一次，
且被 `fcn_0041d89e() != 1` 门控。

**门控函数 `fcn_0041d89e`** 是胜负条件检查：
- `ref_0049911c`（推测：目标天数）与 `ref_00499108`（推测：目标金额）
  同时为 0 时直接返回 0，即无胜负限制、不阻断更新。
- 两个样本存档中这两个字段均为 0。

**实证**：`SAVE1.DAT` 新开局，唯一在场玩家总资产 300,000，
初始资金 300,000 → 指数 = 1，**与存档记录完全一致** ✓

**`Save0.dat` 的差异及解释**：该存档记录 `price_index = 5`，
但按公式推算应为 11（唯一在场玩家流动净值 3,320,222 ÷ 300,000）。

最合理的解释是**它是终局存档**：
- 天数计数 `ref_004990e4` = 295，是一局很长的游戏
- 其余三名玩家均已破产（现金/存款全为 0）
- `currentPlayer = 0` 指向一名已出局的玩家，状态处于结束态

推断：阿土伯的资产是在**最后一次日推进之后**才因收取巨额过路费
（并同时令三人破产）而暴涨的，而下一次日推进再未发生，
故指数停留在暴涨前的 5。

**★ 2026-09 补充：机制已查清，解释站得住了。**

用 `tools/disasm.py` 的字节锚定命令重查，拿到三个此前没有的事实：

1. **更新函数是 VA 0x00423acf**（rich4-re 记的 0x00423ad0 差一字节），
   其**唯一运行时写入点是 VA 0x00423b1b**，由回合推进处 VA 0x0041cfbf 调用。
   另两处写入是开局置 1（0x004073b4）与读档还原（0x0044889c）。
   ——即物价指数**只在回合边界采样**，这一条现在是数出来的，不是推测的。

2. **除数确实是开局资金**。开局时 `mov eax, [eax*4 + 0x46cb94]` →
   `mov [0x49908c], eax`，表内恰好 6 档：
   `300000 / 200000 / 100000 / 50000 / 30000 / 10000`。
   这同时说明**开局资金选项就是难度旋钮**——选得越少，通胀越快。
   （已登记为 `rules/setup.ts` 的 `GAME_INITIAL_FUNDS`。）

3. **出局者被排除在平均之外**（`cmp byte [+0x15], 0 / je skip`）。

第 3 条是解开疑点的关键：**「按存档状态套公式得 11」这个算法本身就用错了
样本**。它只按终局时唯一存活的阿土伯算，而**最后一次真实采样发生在其余三人
尚未出局时**——那时分母是 4、分子还摊进了三个穷人，平均自然低得多。
把三人算作在场重算，结果正落在 5 这一档。

所以：**存档里的 5 是对的，拿终局状态套公式才是错的。**
`rules/wealth.test.ts` 里加了一个用例把这个机制显式钉住。

⚠️ 仍未做的事：没有用原版实机复现「破产当日资产暴涨」的过程。
上面是**基于反汇编的结构性解释加数值自洽**，不是实机验证。
代码按 SAVE1 已验证的公式实现，不做任何迁就 Save0 的特殊处理。

## 逆向源自身的错误（本项目已按汇编校正）

### E-001：`csrc/fortune.c` 的 case 15 转录错误

`rich4-re/csrc/fortune.c` 的 `fortune_check()` 中：

```c
case 15:
    ch = players[current_player].traffic_method;
    if (ch > 2) return 0;
    if (ch == 0) { *v = 15; }        // ← 映射到自己
    else if (ch == 2) { *v = 16; }
    return 1;
```

这破坏了 14/15/16 三个事件的对称性：

| case | traffic=0 | traffic=1 | traffic=2 |
|---|---|---|---|
| 14 | 不变(14) | → 15 | → 16 |
| 15 | **C 版写 → 15** | 不变(15) | → 16 |
| 16 | → 14 | → 15 | 不变(16) |

按 14 与 16 的规律，case 15 在 `traffic == 0` 时应映射到 **14**。

**汇编证据**（`rich4.asm` `loc_0044bdd1`，即 case 15 的分支）：

```asm
loc_0044bdd1:
mov  ch, byte [eax + (_rich4_all_players_state + 17)]   ; traffic_method
cmp  ch, 2
ja   short loc_0044be0d                                  ; > 2 → 不可行
test ch, ch
jne  short loc_0044bde8
loc_0044bde0:
mov  dword [edx], 0xe                                    ; ★ *v = 14，不是 15
```

另一佐证：整个 `fcn_0044bb4b` 中对 `[edx]` 的写入**只有 7 条指令**
（`0xa, 0xb, 0xc, 0xd, 0xe, 0xf, 0x10`），而 C 版在 case 14/15/16 里写了 6 处，
说明这三个 case 在汇编中共用同一组写入路径。

**统一规律**：
```
case 14/15/16:
    if (traffic_method > 2) return 不可行;
    eventId = 14 + traffic_method;
```

**处置**：本项目按**汇编**实现（`packages/core/src/events/fortune.ts`），
并有专门测试 `case 15 + traffic=0 映射到 14` 固化。

> 建议后续向上游 `rich4-re` 反馈此转录错误（DEVELOPMENT_PLAN.md R6）。

### Q-002：购地卡的敌意更新是空操作（原版 bug）

原版 VA 0x004423c4 计算了一个浮点敌意值：

```asm
ecx = land_price * price_index
fild  dword [esp]              ; ecx
fild  word  [esp + 4]          ; level
fadd  dword [0x46531c]         ; + 2.0
fdiv  dword [0x465320]         ; / 5.0
fmulp st(1)                    ; → land_price × pi × (level + 2) / 5
sub   esp, 8
fstp  qword [esp]              ; ★ 压入 8 字节 double
push  edx / push esi
call  0x40df69                 ; update_hostility
add   esp, 0x10                ; 清理 16 字节
```

但 `update_hostility`（VA 0x0040df69）的序言是 `push ebx; push edi`，
其第三个参数取自 `[esp + 0x14]`，是 **4 字节 int**：

```asm
0040df69  push ebx
0040df6a  push edi
0040df6b  mov  edx, dword [esp + 0xc]    ; arg0 victim
0040df6f  mov  ebx, dword [esp + 0x10]   ; arg1 from
0040df97  mov  ecx, dword [esp + 0x14]   ; arg2 delta ← 4 字节
```

对比均富卡的调用现场，它压的是 `push eax`（int），完全吻合。
而购地卡压了 double，被调方读到的是**其低 32 位**。

**实测**：在 840 种真实参数组合下（地价 1000~8000、物价指数 1~20、
等级 0~5），该低 32 位**无一例外为 0**——因为这些结果都是低位为零的
"整齐"浮点数。

**处置**：按 C-FID-4 原样保留，本实现同样不产生敌意。
原版意图公式记录在 `packages/core/src/cards/buy-land.ts` 的
`intendedBuyLandHostility`，并有测试固化「低 32 位恒为 0」这一事实。

### Q-FAC-1：设施的 `type` 在地图数据里恒为 0

过路费按 `facility.type`（+0x18）分三路（见 `rules/facility.ts`），
但**全部 8 张地图、59 个设施的 type 都是 0**，而 0 恰好是「不收费」分支。

已排除的解释：
- 不是偏移读错。同一结构里 `+0x22`(地价)、`+0x24`(房价)、

  且设施最高等级表（VA 0x00474940 = `[1,5,5,1,5,…]`）给
  type 1/2 的上限 5 正好对应 5 档租金。偏移若错，这些不可能同时成立。

因此 `type` 应当是**运行时赋予**的——多半在玩家买下并选择经营方向时写入。
候选线索：`+0x1b` 在地图数据里**有值且因设施而异**（观察到 1 / 4 / 7），
但尚未找到它与 `type` 的关系。

`rules/facility.test.ts` 里有一条断言把「地图数据中 type 恒为 0」
**记录为现状**。若日后该断言失败，说明找到了 type 的真正来源，
届时应回来更新本条，而不是放宽断言。

### 监狱／医院：已定位的结构（尚未实现）

两者结构**完全对称**，偏移相差约 0xF30，可以对照着做。

| | 监狱 | 医院 |
|---|---|---|
| 计数字段 | `+0x34` | `+0x35` |
| 落点处理入口 | `0x0043d304` | `0x0043e9a4` |
| 释放函数 | `0x0043d7bf` | `0x0043ee6e` |

**已确认的规则片段**

- 刑期**由调用方以参数传入**（`[esp+0x18]`），不是常量。
  - 新判：`counter = days`（VA 0x0043d65d）
  - 加刑：`counter = (existing + days) & 0x7f`（VA 0x0043d6c5..0x0043d6d0）
    ★ 末尾的 `and ch, 0x7f` 是为了防止加法进位误置「待释放」位——
    这反过来印证了 0x80 是状态位而非计数的一部分。
- 释放函数对**玩家**（索引 < 4）走 `call 0x0040d6be` 并清空
  `byte [idx + 0x496b30]`；索引 >= 4 是地图上的物件／NPC，另走一套
  （表在 `0x498e28`，步长 0x10）。
- `0x496b30` 是一张 **8 项的字节表**，落点处理开头有
  `for (i=0; i<8; i++) if (!table[i]) break;`——看形状是牢房／病床占用表，
  满员（i==8）时直接返回，**语义待确认**。

**尚未做的**：两个入口函数体内混着大量图素加载（`0x450441`）与对话框，
规则需要从中剥离；刑期的**实际取值**要到各调用点去找。

### D-002：设施 type 1/2 的转盘倍数暂取 1

`rules/facility.ts` 已解出 type 1/2 的计费方式是
`单价 × 转盘倍数`，倍数来自一个 UI 转盘（`0x0044090e`）。

⚠️ 这是一处**有意的已知偏差**，不是遗漏。接上转盘 UI 后即可消除。

### ~~Q-STOCK-2~~：企业资产额已接入（**已结案**）

上市企业记录的 **+0x24 (u32) 就是企业资产额**，即股市均值回归的锚点
（`fcn_004291d6` 取 `commercial[idx].field_0x24 / 10000`）。

实证：臺灣人壽 400000 → 40，与股票表里的初始价 40 一致；
地图 1 的四家企业资产额恰好都是「初始股价 × 10000 × 0.8」。

同时补上了开局的绑定（`_rich4_init_stock_commercial` VA 0x00428cb1）：
数值表里的 `hasCommercial`（0/1）在开局时会被**改写成 1 基企业序号**，
之后 `commercialIndex` 才是可用的下标。

⚠️ 仍缺的是**运行时**联动：原版买下企业后资产额会变，股价随之被拉动；
本引擎目前只在开局读一次静态资产额（企业的运行时归属尚未建模，
见 Q-NEWS-1 同一条根因）。

### ~~Q-GND-2 / Q-GND-3~~：底图格式已完全解出（**已结案**）

这两条都是**误判**，源头是同一个错误的前提。记在这里作为方法论教训。

当时的推理：文件长 5319312，减去 16 字节头与 512 字节调色板，
余下恰好能被 5184 整除得 **1026**，于是认定「每块 1026 字节」。
在这个前提下怎么摆都摆不对，于是又派生出两个问题：
多出的 2 字节在块首还是块尾（Q-GND-2）、块该怎么摆（Q-GND-3）。

真相来自原版地图加载代码 VA 0x00407b66：
```asm
memcpy(0x48b6b4, ground + 0x10, 0x200)   ; 调色板
[0x48bac4] = ground + 0x210              ; ★ 块排布表
[0x48bacc] = ground + 0x2a90             ; ★ 像素数据
```
`0x2a90 − 0x210 = 10368 = 5184 × 2`。即：

- `0x210` 起是 **5184 项 u16 的块排布表**（0..5183 的一个排列）
- `0x2a90` 起才是像素，**每块 1024 字节**，共 5308416 = 2304²

**根本没有「每块 1026 字节」这回事**——1026 = 1024 + 2 是把两张表
当成了一条记录。块间那圈 32 像素错位，就是排布表没被用上的后果。

★ 教训：**能整除不等于是记录长度**。症状（字母被切开、接缝 16.4
对块内 9.3）早就看见了，却一直在「这些块该怎么摆」的框架里找答案，
没有回头质疑「块到底是不是 1026 字节」。
解开它的是去 exe 里读加载代码——**一次反汇编胜过十次统计拟合**。

### ~~Q-SPRITE-1~~：地块建筑与特殊格的资源编号（**已结案**）

两半都解开了，都是从原版代码直接读出来的，不是拟合。

**特殊格装饰**：节点的 `decorIndex` 就是 `map.mkf` 资源 24（58 张）里的
**1 基下标**——八张地图上 decorIndex 的最大值恰好是 58。
图成对排列（偶数普通 / 奇数带粉色光环）。

**地块建筑**：地图加载代码 VA 0x00407e0b 一次载入 5 个等级的图集
```asm
esi = game_stage*4 + game_map               ; global_map_id
for (ebx = 0; ebx < 5; ebx++)
    load(map.mkf, esi*5 + ebx + 0x27)       ; ★ 地图×5 + 等级 + 39
```
绘制时按等级取（VA 0x004091df，等级 0 不画建筑）。故
**等级 L（1..5）→ 资源号 `global_map_id*5 + (L−1) + 39`**，
即资源 39..78 共 40 项（8 张地图 × 5 级）。
连锁店（`land.type != 0`）另有一张：资源 `global_map_id + 0x4f`（79..86）。

先前试图用「风格数 × 5」去凑 259 这个数，方向从一开始就错了。

★ **顺带纠正一处误读**：地块记录的 `+0x1b` 曾被当成「建筑风格号」，
其实是**朝向**。绘制代码 VA 0x004091af：
```asm
al = byte [land + 0x1b]
al += byte [0x499088]      ; ★ 当前视角旋转
dl = 8 - al ; dl &= 7      ; → 精灵图号 0..7
```
它取值 0..7、同区一致，所以看着像风格号——其实是「同一区的房子朝同一个
方向」。这也解释了每个建筑资源为何恰好 8 张图：**那是 8 个朝向**。
`[0x499088]` 是视角旋转，说明原版地图**是可以转的**，日后做视角旋转
直接能用这条。

### ~~Q-COM-1~~：企业的持股排名与归属（**已结案**）

### ~~魔法屋~~：两个转盘都已解出（**已结案**）

魔法屋不是「选一个功能」，是**两个转盘**：

```
效果  jmp [option    * 4 + 0x00431c7a]   12 项
目标  jmp [criterion * 4 + 0x00431812]   12 项
```

目标筛出来写进 `[0x48c380]`（最多 4 人），效果再**对名单里每个人逐一执行**。
所以「變賣所有卡片」卖的不是自己的牌，是被点到的那些人的。
实现见 `places/magic-house.ts`。

转盘的转法（VA 0x0043390b）有三处不照直觉：

- **先抽目标**（`rand() % 12`），选不出人就重抽。
- **名单里有自己 → 效果直接定为 6「得一張卡片」**，不再抽效果。
- 否则 `effect = rand() % 11`，且 `if (effect == 6) effect = 7`。
  ★ 于是**第 11 条「拍賣當格土地」永远转不到**，第 6 条也只有
  「点到自己」时才会出现。效果派发函数 `0x431caa` 全局只有这一个调用点，
  所以这不是漏看了别的入口——它就是**没接线的内容**。

顺带钉死两件事：
- **`sex` 的编码**：非 0 是男、0 是女（由「所有男生／所有女生」两条筛选器
  的 `je` / `jne` 方向反推）。`Player` 因此新增 `isMale`。
- **變賣类效果按標價全额入點券**，不是百貨公司那个九折——
  两处走的是不同的代码（0x441f21 / 0x445b3f vs 0x42d145 / 0x42d1b2）。

### ~~Q-OBJ-1~~：物件落点效果（**已结案**）

十八种物件踩上去各自会怎样，已逐条译出，见 `rules/object-landing.ts`。
派发是一张 18 项跳表 @ VA 0x0041b3e5，下标 = 种类 − 1：

| 种类 | 物件 | 落点效果 |
|---|---|---|
| 1..10、12 | 財神/福神/窮神/衰神/天使/惡魔/土地公 | 附身 7 天，加三项修正 |
| 11 | 惡犬 | 徒步 → 住院 3 天；**有车就咬不到** |
| 13 | 禮物 | 按全局库存加权抽一个 1..8 号道具 |
| 14 | 寶箱 | 點數 +500 |
| 15 | 死神 | ★ **什么也不发生** —— 它是自己追上来的 |

- **「停下来」才生效**：除路障外全都要 `[0x48baf8] == 0`。
  这也说明整个处理函数是**每走一格跑一次**的，不是回合末——
  炸彈的引信因此按格走，路障因此能在半途拦人。

  全局只有 0x0040e205（减）与 0x0040ebec（加）两条写指令。
- **`blessing_level` 有三种用法**，不是一种：`(0,0)` 獎金、`(0,1)` 罰金、
  `(1,1)` 劫难。后两种的档位与第一种**正好相反**，且第三种读的是
  `+0x48` 而不是 `+0x46`。先前只实现了第一种并当成通用规则，
  直接拿去算罚金会算反。
- **搭档机制**：神明离场时，下标 0..11 的会换成**配对的另一个**登场
  （小財神↔大財神、惡犬↔土地公……）。开局只放「小的那一半」，
  大神要等搭档被请走才出现。
- **炸彈会传染**：引信没走完而同格有别人时，塞给**下标最小**的那位
  （`0x40d293` 取位图最低位，不是随机）。

### Q-OBJ-2：物件重新登场的落点挑法未完全解

`place_object` 的目标格由 `pick_object_node`（VA 0x0040aa6c）挑：

### ~~Q-BEGGAR-1~~：破产者变乞丐（**已结案**）

同一个落点处理函数里，物件派发**之前**还有一段（VA 0x0041b5fd）：

```asm
edi = 同格玩家位图 & ~(1 << 我)          ; node.flags bits 8..11
其他 = lowest_set_bit(edi)
if (其他 != -1 && 其他.who_plays == 0 && [0x48baf8] == 0) {
    金额 = 物价指数 × 1000                ; ((pi*3*8 + pi) * 8) * 5
    sprintf(buf, "施捨給乞丐%d元", 金额)
    pay_money(我, -1, 金额, 0)            ; -1 → 进公库
    call 0x40cc56(其他)                   ; ★ 乞丐收了钱就消失
}
```

★ `who_plays == 0` 就是**已出局**。也就是说破产玩家的棋子留在地图上
当乞丐，谁停在同一格谁掏 `物价指数 × 1000`，钱进公库。
已实现，见 `rules/beggar.ts`。

两处容易想当然的细节：
- **只看下标最小的那个同格玩家**（`0x40d293` 返回位图最低位）。
  他要是还活着就直接跳过，**不会接着往下找**——两个出局者站一起时，
  只有下标小的那个收得到钱。
- `0x40cc56` 不是「乞丐消失」，是**把他挪到别处**（清掉原格占位，
  再 `pick_object_node(原节点)` 挑一格）。所以同一个乞丐还会再遇到，
  只是不会被同一个人在原地反复薅。挪动的落点同样受 Q-OBJ-2 影响。

### D-003：节点坐标与底图零偏移

见 `packages/assets-pipeline/src/ground.ts`。格式解对之后，
103 个节点按 (0,0) 画上去有 **87 个落在非海面上**，而在 ±200 像素范围内
扫描到的最优偏移也只有 91 —— 零偏移已在最优解附近。

仍需注意：用颜色判「是不是海」是**弱判据**（峰又宽又平，它奖励的是
「多少点落在大块绿色里」）。真正的依据是形状吻合：棋盘路线沿海岸走
一圈，西侧支线通澎湖、东南支线通绿岛/兰屿。测试里只断言站得住的部分。
