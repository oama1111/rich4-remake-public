## 一、结论摘要

**核对规模**：状态块逐块清单共 **46 个区块**（= 存档函数 46 处 `fwrite`）。
逐块结论（见 §2.1，**逐个可点算**）：

| 结论 | 行数 | 序号 |
|---|---|---|
| **通过**（✅，或读侧行为与原版一致） | **28** | 0…4、5、9…16、18、21…25、33、34、37…40、42、43 |
| **不通过**（❌ 缺失 / 数值错） | **6** | 17、26、29、35、36、41 |
| **部分 / 无法判定**（⚠️ 只读了一部分，或规格本身未定名） | **12** | 6、7、8、19、20、27、28、30、31、32、44、45 |

> 即：**通过 28 / 不通过 6（5 条「缺失」+ 1 条「数值错」）/ 部分或无法判定 12**。

**三件必须立刻知道的事**：

1. **remake 根本没有「按原版格式写存档」这条路径。**
   存档是带版本号的 JSON（`packages/core/src/loaders/savegame.ts:74-77`），
   原版格式只有**单向导入**（`importOriginalSave`，同文件 `:375`）。
   ⇒ 「remake 写出的存档能被原版读」这条硬指标**当前为 0 实现**。
   这是本主题最严重的一条（`缺失`/`阻断`）。

2. **规格的块序表与读数已复核一致；remake 的 `OFFSET` 常量也逐个正确。**
   机械提取 45 处 `fread`（`call 0x4576d0`）与 46 处 `fwrite`（`call 0x457ada`）的参数，
   与 `save-format.md` §二 的表逐行对照，结论：
   - 表 **42 行**「偏移 / count / size / 目标全局 / 字节」**逐行全对**，
     字节列和 **= 10,055**；
   - `10,055 + 4`（`@source 0x00402b1a` 的 `fseek(file,4,SEEK_SET)` 跳过版本标识）
     **= 10,059**，与 §2.0 的两档闭合式**精确一致**；
   - 写侧 46 = 读侧 45 + 1（写唯一的版本标识），**逐项一一对应、无错位**；
   - 两档的结构常数（`0x274b` / `mapDataSize` / `0x2718`）remake 与规格**同值**。
   ⇒ **本条通过**。remake 的偏移取自真实 `fread` 序，与规格表**同构**；
   已用两个真实存档的字节交叉验证：日期、marketDay、mapDataSize、initialFund、pool、
   news/fortune 牌堆与游标、玩家 0/1 现金**全部对得上**。

   > ⚠️ 过程留档：本条**一度被我判成「规格表偏 4 字节 / 少 2 行」**，原因是
   > 我引用的 `save-format.md` 在核查期间被**并发更新**（185 行 → 337 行，
   > 新增了 §二之二「写侧对称性校验」与 5 条结案说明）。按**当前 337 行版**复算后，
   > 原判断**不成立**，故在此撤回（详见 §十·1）。
   > 教训：引用规格行号时要连版本一起锁。

3. **两个 8 字节区块（`0x496b30` / `0x496b60` = 在狱 / 住院标志，含 8 槽）没有导入，
   而且 remake 现在用的替身表推算法语义上就不等价。**
   两个真实存档的这两块都是 `[1,1,0,0,0,0,0,0]`（玩家 0、1 在狱/住院），
   而 `savegame.ts:484-485` 从 5 条替身记录推占用表，只填 4..7 号槽（NPC），
   0..3 号槽恒为 0 ⇒ **读原版存档会把玩家 0、1 从监狱/医院「放出来」**。

**其余高价值结论**：
- `landPriceStatus`（地图块内 `+0x17`，每日递减的状态字节）原版存了、remake 导入时一律归零；
  `landTenure`（`flast`）同理 —— 而 `map.ts` 其实已经把这两个字段读出来了。
- `0x499088`（视图旋转）remake 完全没有对应字段。
- **`0x499078`（大盘指数）remake 的重算与存档真值差 1（两个样本都差）**：
  `Save0` 74637 → 74638、`SAVE1` 13490 → 13491。根因是一次多余的 `Math.fround`（x87 扩展精度 vs 单精度），
  详见 §八·3。这是本轮**唯一一条可以逐位复现、且改一行就能修好**的数值错。
- 字符串与编码：`#NNNN` 语音码这条线 remake 做得**完全正确**（含 `1050 + 角色×27 + 事件` 与 `@DD` 表情图算式）。

### ★ 规格侧的一处可复核疑点（`gen/strings.json` 的 `text`）

复算时发现 `gen/strings.json` 的 `text` 字段**不是** Big5 解码结果：

```json
{"va": 4198454, "sec": "AUTO", "text": "1骼︺qI", "bytes": 7}
```

而同一份 exe 的字节用 `big5` / `cp950` / `big5hkscs` 三种 codec 都能正常解出（上面实测 7 例全对）。
已试 `python3 tools/rich4strings.py build` 重建（刻意**不保留**该重建结果），
输出仍是 `"1骼︺qI"`，且 `文本→byte` 不可逆（`'骼'.encode('cp950') = c0 66`，不是原字节）。
⇒ **`gen/strings.json` 的 `text` 只能当「有哪些串、在哪」的索引，不能当文本真值**；
需要逐字对齐原文时应直接从 `rich4.exe` 字节 Big5 解码（remake 的 `speech.ts` /
`data/*.test.ts` 正是这么做的）。
**本报告未修改规格侧任何文件**；对 `gen/` 的三份 JSON 做的重建是 `rich4strings.py build`
的常规产物（区间分布 `data 1270 / string 910 / table:data 104 / table:code 64 / bss 1`
重建后与 `02-strings-and-layout.md` §三 的表**逐项相同**，说明重建本身没有破坏结构）。

另外，`02-strings-and-layout.md` §二 写「被指令直接引用 **340** 条」，而 `gen/string-xrefs.json`
