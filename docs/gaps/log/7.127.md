### 7.127 ★★★ 第 144 条（本轮）：魔法屋 idx 1/2 的**实测语义与 PRD 对不上** —— 记录 0 被整个跳过（五组对照一致）

> 这是 §7.122「判据读通、但差分不稳定」的**续查结论**。本轮用**多组对照**把它钉成
> 了一个**确定的现象**，但现象**与 PRD 写的不符**，且两种解释都还站得住（见 §(3)）。

#### (1) 现象（全部可复现；命令见 §(4)）

固定 `[0x499114]=4`（四个玩家都在场）、`[0x498e98]=num_lands`、
`[0x498e84]=记录表基址`，给记录表第 i 笔的 `+0x19`（owner，**1 基**）写归属，
然后 `call 0x431842(kind=1)`：

| # | `num_lands` | owner 写入位置 | 期望（按 PRD） | **实测** |
|---|---|---|---|---|
| 1 | 1 | `base+0x19` = 1（P1 拥有记录 0） | `[1]` | **`eax=0`、空** |
| 2 | 2 | `base+0x19` = 1、`base+0x34+0x19` = 1 | `[1]` | `eax=1`、**`[1]`** |
| 3 | 2 | `base+0x19` = 1、`base+0x34+0x19` = 2 | `[1]` | **`[2]`** |
| 4 | 2 | `base+0x34+0x19` = 1（记录 0 留空） | `[1]` | `[1]` |
| 5（对照） | 2 | `base` 指到 `LAND-0x34`，owner 写 `base+0x34`、`base+0x68` | `[1]` | `[1]` |

**读法**：第 3 组是关键 —— P1 明明拥有记录 0，结果却是 P2；第 1 组更直接：
**只有一条记录、且归 P1，返回 0（一个候选都没有）**。
第 5 组把整表**平移一格**后现象**完全一样**（仍是「第一笔被忽略」）。

⇒ **可靠结论**：这六支「取最大者」扫描地块/设施表时，**第 1 笔记录不参与**；
即 PRD 写的 `for (i = 1; i <= num_lands; i++)` 与实际行为**不符**（实测像是只扫
`i = 1 .. num_lands-1`，或表首有一笔「占位记录」）。

#### (2) 反证也做了：**不是**我的桩写错位置

- 单独跑 `0x4318f2..0x4318ff`（`mov cl,[ecx+edi+0x19] / and ecx,0xff / …`）
  并给 `ecx=base`、`edi=0x34`、记录 1 的 owner 写 7 ⇒ **返回 7**（指令本身没问题）。
- 但把**整支** `0x431842` 跑起来时，同一个「记录 1」位置却算出 **0**
  （`0x4318ff` 处 `ecx=0`，而 `0x4318f2` 处 `ecx=0x601000`）。
  ⇒ 嫌疑集中在 `0x4318f2` 那条 `mov cl, …` **把基址寄存器 ECX 的低字节写坏**
  （CL 与 ECX 同体）—— 要么是原版写错了寄存器、要么是仿真器在这条指令上与真机不同。
  **两者都还没有排除。**

#### (3) 因此本轮**不交付差分**（理由）

PRD 的「数 1..num_lands」与实测「第一笔被忽略」**互相矛盾**，而我没能分清是
(a) 原版真的跳过第一笔（那 PRD 该改），还是 (b) 仿真器在
`mov cl,[ecx+edi+0x19]` 这类「CL 覆盖 ECX 低字节」的模式上不可靠（那该修的是测试台）。
**在分不清之前，按本会话一贯口径：不写会固化错口径的断言。**

- §7.122 已记「不稳定」；本轮的增量是：**把「不稳定」收窄成一个「确定但矛盾」的现象**，
  并给出多组可复现对照。
- 复刻侧 `places/magic-house.ts` 的 `landCountOf`/`houseCountOf` 是否也跳第一笔
  **需另核**（它按 `lands` 数组遍历，口径取决于 loader 是否把第一笔也收进数组）。

#### (4) 复现命令（下一轮直接用）

`cd rich4-spec` 后运行下面这段（注意：**外层用 `PYOUT` 作 heredoc 定界符**，
因为脚本自己要打印 `PY`）：

```bash
cd rich4-spec && .venv/bin/python - <<'PYOUT'
import sys; sys.path.insert(0,'tools')
from emulate import Emu, SCRATCH_BASE
LAND = SCRATCH_BASE + 0x1000
def run(n, owners, tag):
    e = Emu()
    def setup(x):
        x.write32(0x499114, 4)
        for p in range(4): x.write8(0x496B68+p*0x68+0x15, 1)
        x.write32(0x498E84, LAND); x.write32(0x498E98, n)
        x.write32(0x498E88, SCRATCH_BASE+0x8000); x.write32(0x498E8C, 0)
        for i, o in enumerate(owners): x.write8(LAND+i*0x34+0x19, o)
        for i in range(8): x.write8(0x48C380+i, 0xEE)
    r = e.call(0x431842, [1], setup=setup, timeout_insns=200000)
    print('%-28s -> eax=%d arr=%s' % (tag, r['eax'], list(e.read(0x48C380, 4))))
run(1, [1], 'n=1 P1 rec0 only')
run(2, [1, 1], 'P1 rec0+rec1')
run(2, [1, 2], 'P1 rec0, P2 rec1')
PYOUT
```

#### (4b) ★ 追加的两轮反证（本轮）：补丁版**更坏**、`num_lands` **也不是**扫描上界

**(a) 把 `mov cl,[ecx+edi+0x19]` 补丁成 `mov dl,…`（并在下游把 `ecx` 一并改成 `edx`）
⇒ 结果 **更坏**（六组对照全部变成 `eax=0`）**，而不是变好**。
若原版真是「数错寄存器」，补丁**应当**修好它 —— 没修好，说明**不是**单纯的笔误，
或者我的补丁本身有副作用（`edx` 在 `0x4318ff` 之后正是**计数器**：
`0x431903 inc edx` 数的是「拥有多少块」，所以把归属读进 `edx` 会把它冲掉，
**这条反证因此不干净**，我如实标出）。

**(b) `[0x498e98]`（`num_lands`）**也不是**循环上界**：固定「只有记录 1 归 P1」，
把 `num_lands` 从 1 调到 4，**六次结果完全一样**（都返回 `[1]`）；
「只有记录 2 归 P1」+ `num_lands = 3/4` 同样都命中。
⇒ 那个 `cmp eax, [0x498e98] / jg` **不构成**我原先设想的上界
（要么该全局在别处被改写，要么这一支读的不是它）。

**结论收窄为**：PRD 写的「`for (i = 1; i <= num_lands; i++)` 遍历第 1..n 笔」
与他**实测不符**（记录 0 从不参与、`num_lands` 也不封顶），但**正确的模型还没建立**。
⇒ 下一轮的正解不是继续打补丁猜测，而是**换一个不依赖这条指令的取证方式**：
用 `UC_HOOK_MEM_READ` 把整支 `0x431842` 对记录表的**每一次读**（地址+值）打出来，
直接看它到底读了哪些记录 —— 那比推寄存器干净。

#### (4c) ★ `UC_HOOK_MEM_READ` 取证（本轮）：整支只读了**记录 1 的 owner**，读了 4 次

按 §(4b) 的建议改用**读追踪**（不推寄存器）：

```python
# 固定：rec0->P1(0x601019=1)、rec1->P2(0x60104D=2)、num_lands=2、四人全在场
def h(mu, access, addr, size, val, user):
    if LAND <= addr < LAND+0x80:
        print(hex(addr), hex(mu.reg_read(UC_X86_REG_EIP)))
e.mu.hook_add(UC_HOOK_MEM_READ, h)
```

实测输出（`eip` 十进制换算是 `0x4318F2`）：

```
addr=0x60104d eip=0x4318f2     ← 记录 1 的 owner
addr=0x60104d eip=0x4318f2
addr=0x60104d eip=0x4318f2
addr=0x60104d eip=0x4318f2
结果：eax=1 arr=[2]            ← 判给 P2
```

**两条新事实**（都干净、不依赖寄存器推断）：
1. 整支对记录表的**唯一**读点就是 `0x4318f2`，而且**只读记录 1**（`0x60104d`）——
   **记录 0（`0x601019`）一次都没被读**。这独立复现了 §(1) 的「第一笔被忽略」。
2. 同一个地址读了 **4 次**（不是 1 次）⇒ 那句 `cmp eax,[0x498e98]` 在这条路径上
   **没有**起到「按 num_lands 收口」的作用。
3. 且 `call` 前后记录表**完好**（`before == after == (1, 2, base)`）⇒ 不是「表被清掉」。

⇒ **可靠结论**（本轮）：**实现与 PRD 的「遍历第 1..n 笔」不符**，
且这一支的行为无法用「寄存器推断」还原。
**仍缺的一步**：读追踪只给了地址序列，没给**循环控制**；要建成模型还需要
在 `0x4318e1`/`0x431907`（地块循环的两端）与 `0x4318be`/`0x431963`（玩家循环两端）
各挂一个 code hook，把 `eax`/`ebx`/`edx` 的**轨迹**打出来 —— 那是下一轮第一件事。

**给复刻的处置建议（保守）**：`places/magic-house.ts` 的 `landCountOf`/`houseCountOf`
**暂不改** —— 现有实现（数 `lands`/`facilities` 里 owner 匹配的全部条目）在
「无平手 + 每条记录都有效」的常见场景下与 PRD 一致；在**未建立正确模型之前**改它，
风险大于收益。本条作为**未决项**留在 §7.3 第 14 项旁边。

#### (4d) ★★ 定论（本轮收口）：**读集合 = 记录 1..num_lands**（记录 0 永不参与）

把 §(4c) 的读追踪按「记录号」归并（记录号 = 偏移 / 0x34），并扫 `num_lands` 与人数：

| 设置 | 读到的记录号 |
|---|---|
| `players=1, num_lands=1` | **`[1]`** |
| `players=1, num_lands=2` | **`[1, 2]`** |
| `players=1, num_lands=3` | **`[1, 2, 3]`** |
| `players=4, num_lands=2` | **`[1, 2]`** |
| `players=4, num_lands=4` | **`[1, 2, 3, 4]`** |

⇒ **干净、可复现的定论**：这一支扫描的记录集合**恰好是 `1..num_lands`**，
**与人数无关**，且**记录 0 一次都不读**。

★★ **因此 PRD 那句「`land_info[1..num_lands]` 中 `+0x19 == 玩家+1` 的个数」
的「集合」是对的，但「判据」不可信**：
`0x4318f2` 的 `mov cl,[ecx+edi+0x19]` 之后接的是 `and ecx,0xff`，
而 `CL` 与基址寄存器 `ECX` **同体** ⇒ 这个模式的语义无法用「读 `+0x19` 得归属」
来解释（三轮反证：换 `dl` 更坏、`num_lands` 不是上界、读集合却完全稳定）。
**要么原版这一段确实写错了寄存器，要么本仿真器在这条指令上不可靠 —— 未分辨。**

**给复刻的处置（本轮定稿，保守）**：`places/magic-house.ts` 的
`landCountOf`/`houseCountOf` **不改**。理由：读集合 `1..n` 与现有实现
（遍历 loader 给出的 `lands` 数组）在**常见场景**下等价，而**归属判据**这一层
既然原版不可信，复刻按「正确语义」实现是**更好的选择**，且已被
`magic-house.test.ts` 覆盖。**若日后建成通道 3 的原版预言机**，应回来重测这一支，
届时再决定是否照抄原版的（可疑）行为。

⇒ 本条**收口**：不再在本会话继续追这条指令；把「读集合 = 1..n」这条确定事实
与「判据不可信」的结论留档即可。
