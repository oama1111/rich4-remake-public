#### (2) ★★ 顺带解出替身记录的字段身份（结掉一条悬了很久的「未决」）

冬眠卡（卡 15）写 `+0x0c`（`0x498df4`）= 5、清 `+0x0d`；梦游卡（卡 16）**先查 `+0x0c`**，
为 0 才写 `+0x0d`（`0x498df5`）= 5。⇒ **`+0x0c` = 冬眠天数、`+0x0d` = 梦游天数**，
两者互为「不可叠加」（已在冬眠的替身不会再被梦游覆盖，反之亦然，**先到者说了算**）。

这把 `cards.md` 卡 15 那条「`0x498de8 + i*16` 的 `+0x0a/+0x0c/+0x0d/+0x0e` 与
`player+0x36/+0x37/+0x38` 的对应关系未确认」**从推测升级为两卡互证**；
复刻侧 `SpecialActor.hibernating` / `sleepwalkDays` 与 `loaders/save.ts` 的 `+12` / `+13`
映射正是这一对，**无需改动**（原本就按存档布局写对了）。

#### (3) ★ 测试台教训（已补进 `verification.md`）：`pushad/popad` 会连 `eax` 一起还原

`has_card` 数据表桩第一版把 `movzx eax, byte [ebx+ecx]` 放在 `popad` **之前** ⇒
返回值被还原成进入时的值 ⇒ **所有防御卡查询都返回 0**、免罪/嫁禍/復仇三条支一条都不走，
而桩本身看不出任何毛病（9 个红用例全是这一个原因）。
**要返回值的桩必须 `…计算 → mov [槽],eax → popad → mov eax,[槽] → ret`。**
