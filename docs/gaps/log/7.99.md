#### (2) ★ 工具踩坑：`eval_block` 里**栈局部量必须在 `reset()` 之后直接写**

本轮想用「跑公式片段」的方式复现上面三支（`eval_block(0x41a168, 停址)`），
一开始怎么都不对。根因值得记下来，因为**下一个做同类片段驱动的人一定会踩**：

```python
emu.eval_block(0x41A429, 0x41A446, regs={'edx':0x600000}, setup=s)
#                                    ▲ setup 在 reset() 之后、regs 之前被调用 ⇒
#                                      s() 里写的 [STACK_TOP+0xe0] 会被**旧栈内容**顶掉，
#                                      而 `mov edx,[esp+0xe0]` 读到的是默认/残留值。
```

- `eval_block` 的顺序是 `reset()` → `setup()` → **写 `regs`** → 写 `ESP` → 跑；
- 而 `reset()` **不会清栈**，所以 `setup()` 里对 `[STACK_TOP+…]` 的写入是**有效**的 ——
  但如果 `s()` 还依赖「某个寄存器已经等于 0x600000」去算地址，就得**先写段址**；
- 更稳的姿势（本轮的结论）：**凡是「块内会读栈局部」的驱动，都把栈局部写在
  `setup()` 的最后一个动作里**，并且**不要**在 `setup()` 里依赖 `regs` 的值；
  需要段址时用**常量**（如 `0x600000`）写进内存，而不是先读 `[0x498E88]`。
- ★ 另一个同族事实：`MkfArchive` 的段址是**我们选的**（`SCRATCH_BASE`），
  但**原版读的是它自己的全局**（如 `0x498E88` 的设施表基址）⇒ 两者都要设，
  少一个就表现为「读未映射地址」。

`packages/core/src/rules/facility.test.ts` 的 239 行覆盖，不再另建片段驱动。）
