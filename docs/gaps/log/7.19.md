### 7.19 ★ 第 37 条（本轮）：神明加持三个真 bug —— 12 个事件金额不吃加持、2 个读错字段、每次事件多掷一次随机数

#### (1) 事件表的 `blessing` 只有 16 条，实际 **28 条** —— 12 个事件完全不吃加持

`_rich4_blessing_level`（`VA 0x44b896`）有三条同构的用法（`reward` / `penalty` / `misfortune`），
`blessing.ts` 早就把三条都实现了。但**事件表**里只给 16 个事件标了 `blessing`，
其中还有两条记错。

★ **关键：不能只看事件函数体里有没有 `call 0x44b896`。** 事件 19 的函数体
（`0x44d1e0`，21 条指令）**一条 call 都没有** —— 它靠 `jne 0x44d172` 跳进**共享尾**：

```asm
; penalty 尾 @source 0x0044d172 —— 17/18/19/23/24/26/30 都走这里
0044d172  push 1 / 0044d174 push 0 / 0044d176 call 0x44b896
; reward 尾 @source 0x0044d2a9 —— 20/21/22/25/27/28/29/31 都走这里
0044d2a9  push 0 / 0044d2ab push 0 / 0044d2ad call 0x44b896
```

把「谁跳进这两条尾」穷举一遍（新探针 `tools/scratch/blessing_callers.py`）后：
**28 个命运事件带加持**（15 个直接调用 + 13 个经共享尾），`id 16` 是原版**没接**的那一个。
表里的实际状况：

| 问题 | 事件 | 后果 |
|---|---|---|
| 漏记 12 条 | 18、20、21、23、24、25、26、27、28、29、30、31 | **这些事件的金额完全不吃神明加持**（`罰款/獎金` 都不会被加倍或免掉） |
| 记错用法 | 19 记 `reward`（实为 `penalty`）、22 记 `misfortune`（实为 `reward`） | 读错字段（`+0x48` ↔ `+0x46`）且档位语义相反 ⇒ 财神附身反而让你多付一倍 |

语义交叉验证（不是只看汇编）：28 条里**每一条 `effects: ['pay']` 都是 `penalty`、
每一条 `['give']` 都是 `reward`**，而 `misfortune` 只给那些没有金额的灾难事件
（6/7/10/11/12/32/33）—— 与「免付罰金／罰金加倍」「獎金加倍／獎金作廢」六条提示语完全自洽。

**新测试直接读 exe 字节**（`packages/data/src/event-table.test.ts`）：
对每个调用点取出 `6a <arg1> 6a <arg0> e8 <rel32>`，校验 `rel32` 确实指向 `0x44b896`，
再由压栈组合自行判定用法，最后与事件表逐项比对。
⇒ 表与 exe **任何一侧改了都会红**（已实测：把 id 20 改成 `penalty` 立刻失败）。

#### (2) 簇 C：命运事件**每次都多掷一次随机数**

```ts
// 先前（错）：无条件掷
const coinFlip = rng.next() & 1;
```
`@source 0x44b8c1` 的分档是 `cmp si,0x64 / jle 查50` → `cmp si,0x32 / jle 查负`
→ **只有 `50 < 加持值 ≤ 100` 那一档才 `call 0x456f2d`**。
先前无条件掷，而 `rngState` 又写回了状态 ⇒ **每一次带神明加持的命運事件都让随机序列多走一步**，
之后所有随机事件整体错位。已改成按档位条件掷，并加了两条可证伪的测试：

- 加持值 ∈ {200, 101, 50, 0, −1} ⇒ 整场结算 `rngState` **一个字节都不动**；
- 加持值 ∈ {75, 100} ⇒ **恰好前进一次**（用手工推一步作真值）。

（事件 2「冒貸」自身不掷随机数，正好当探针。实测把 `needsRoll` 强制为 `true` 时第一条立刻红。）

这是本文件第 8/9/10 条修过的**同一类错误**，也是续做指南第 4 项（AI `aiRoll`）之外的又一处。
