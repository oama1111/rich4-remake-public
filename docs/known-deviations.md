## D-001：随机数播种策略按模式区分

| | |
|---|---|
| **类别** | **单机：零偏离**（完整复刻原版）｜**联机：新增行为**（原版无联机，无对应物可偏离） |
| **影响** | 不影响任何概率分布 |
| **状态** | 已实施（`packages/core/src/rng/policy.ts`） |

> **修订记录（2026-09-13）**：本条最初的方案是「全局改为显式注入种子」，那会让单机
> 失去原版的"读档重开刷结果"。经复核，这是把**引擎确定性**与**存档策略**两件事
> 混为一谈了。拆开后两者可以同时满足，单机的偏离**完全消除**。见下方「最终方案」。

### 原版行为

原版全程序共 **3 处** `srand()` 调用，**全部**以 `GetTickCount()`（系统启动至今的毫秒数）为种子：

| 地址 | 位置 | 时机 |
|---|---|---|
| `0x0040170F` | `asm/rich4_initialize.asm:146` | 游戏启动，DirectDraw 初始化后 |
| `0x00402FA1` | `asm/rich4_save_files.asm:507` | **读档之后** |
| `0x0041D06E` | `asm/rich4_player_core_actions.asm:4830` | 回合/新一天推进时 |

因此：
- 原版存档**不保存 PRNG 状态**；读档后重新播种，所以"读档重开会刷出不同结果"是**原版的真实行为**。
- 每回合都会用挂钟重新播种，PRNG 序列在回合之间被打断。
- **原版对局本质上不可复现。**

### 最终方案

关键是把两件**本不相干**的事拆开：

| 关注点 | 要求 | 由谁决定 |
|---|---|---|
| **引擎确定性** | `reduce(state, action) → state` 必须是纯函数 | 引擎本身，两种模式**都成立** |
| **存档是否写入 PRNG 状态** | 决定能否"读档刷结果" | 存档**策略**，按模式取不同值 |

做法是把「重新播种」表达为 action 流中的**一条显式 action**，而非让引擎去读挂钟。
非确定性因此被捕获成 action 日志里的**数据**，引擎保持纯函数。

| | 单机 `SINGLE_PLAYER_POLICY` | 联机 `MULTIPLAYER_POLICY` |
|---|---|---|
| PRNG 算法 | 位级一致 | 位级一致 |
| 存档写入 PRNG 状态 | **否** | 是 |
| 重新播种时机 | 启动 / **读档后** / **每回合**（与原版三处 `srand` 逐点一致） | 仅开局一次 |
| 读档重开刷结果 | **可以**（原版行为） | 不适用 —— 联机没有"读档"这个动作 |
| 断线重连 | 不适用 | 服务器下发含 PRNG 状态的完整快照，属**重同步**而非读档 |

### 为什么单机算「零偏离」

单机模式下，播种时机与原版三处 `srand(GetTickCount())` **逐点对应**，存档同样不含
PRNG 状态，因此「读档重开刷结果」这一原版特性被**完整保留**。玩家可观测的行为与原版
没有任何差异，故不构成偏离。

### 为什么联机算「新增」而非「偏离」

原版**没有联机模式**，不存在可供偏离的原版行为。联机的确定性播种是全新设计，
用于满足 DEVELOPMENT_PLAN.md §5.2 **C-DET-4**（断线重连、反作弊、赛后回放）。
它不改变任何一条游戏规则或概率分布。

### 附带收益

因为 reseed 值被记入 action 日志，**单机局同样可以完整回放**——
调试、复盘、bug 复现都能用，而这是原版做不到的。

### 溯源

- 原版 PRNG：`Rich4/rich4.exe` VA `0x00456F2D`（反汇编原始二进制确认）
- 原版三处 `srand`：`0x0040170F`（启动）、`0x00402FA1`（读档后）、`0x0041D06E`（回合推进）
- 实现：`packages/core/src/rng/watcom.ts`、`packages/core/src/rng/policy.ts`
- 测试：`packages/core/src/rng/watcom.test.ts`、`packages/core/src/rng/policy.test.ts`
  （其中「读档重开能刷出不同结果」与「重连恢复后结果完全一致」各有专门用例）

## ⚠️ 陷阱记录（非偏离，但必须避免）

### T-001：不要沿用 rich4-re 的 `mscrt.ld` 随机数映射

`rich4-re/asm/mscrt.ld:15-16` 把原版的 CRT 随机数重定向到了 msvcrt：

```
PROVIDE(_libc_srand = _srand);
PROVIDE(_libc_rand  = _rand);
```

msvcrt 的 `rand()` 用的是乘数 `0x343FD`、增量 `0x269EC3`，与原版 Watcom 的
`0x41C64E6D` / `0x3039` **完全不同**。

**后果**：逆向项目构建出的 `rich4_mscrt.exe` 虽然能运行，但**随机序列已与原版不同**。
任何从该可执行文件观测到的随机行为都不可作为保真依据。

正确做法是以**原始 `rich4.exe` 的反汇编**为准，本项目已如此实施。

## 已查明的原版机制（非偏离，存档实证）

### F-001：开局资金分配

| 项 | 值 | 证据 |
|---|---|---|
| 初始资金 `_rich4_game_initial_fund` | **300,000** | `Save0.dat` 与 `SAVE1.DAT` 偏移 `0x268A` 均为 300000 |
| 开局现金 | `初始资金 × init_cash_ratio / 100` | 见下表 |
| 开局存款 | `初始资金 − 开局现金` | 同上 |

`SAVE1.DAT` 是一局刚开始的游戏，四名玩家的现金/存款拆分**精确匹配**各自角色的
`init_cash_ratio`（该字段来自 `rich4_characters.c`）：

| 玩家 | 角色 | 现金 / 存款 | 现金占比 | 角色的 `init_cash_ratio` |
|---|---|---|---|---|
| 1 | 孫小美 | 150,000 / 150,000 | 50% | **50** ✓ |
| 2 | 阿土伯 | 120,000 / 180,000 | 40% | **40** ✓ |
| 3 | 金貝貝 | 240,000 / 60,000 | 80% | **80** ✓ |
| 0 | 小丹尼 | 150,000 / 150,000 | 50% | 55（见下） |

现为 150,000 / 150,000，差额恰为一笔 15,000 的银行存入。故不构成反例。

> 这同时解答了 M1 阶段留下的疑问（「小丹尼 ratio=55 却是 50:50」）。

### F-002：物价指数的更新时机与公式（原 Q17，已结案）

**公式**（`rich4_update_price_index.asm`）：
```
新指数 = (在场玩家总资产之和 ÷ 在场人数) ÷ 初始资金      // 两次均为 idiv，向零取整
if (新指数 > 当前指数) 当前指数 = 新指数                  // 只升不降
```
「在场」的判据是 `cmp byte [player+0x15], 0`，即 **who_plays 整个字节非 0**。

**调用时机**：全程序**仅一处**调用，位于日期推进函数 `fcn_0041cf67`
（`rich4_player_core_actions.asm:4761`），即**每推进一天**更新一次，
且被 `fcn_0041d89e() != 1` 门控。

**门控函数 `fcn_0041d89e`** 是胜负条件检查：
- `ref_0049911c`（推测：目标天数）与 `ref_00499108`（推测：目标金额）
  同时为 0 时直接返回 0，即无胜负限制、不阻断更新。
- 两个样本存档中这两个字段均为 0。

**实证**：`SAVE1.DAT` 新开局，唯一在场玩家总资产 300,000，
初始资金 300,000 → 指数 = 1，**与存档记录完全一致** ✓

**`Save0.dat` 的差异及解释**：该存档记录 `price_index = 5`，
但按公式推算应为 11（唯一在场玩家流动净值 3,320,222 ÷ 300,000）。

最合理的解释是**它是终局存档**：
- 天数计数 `ref_004990e4` = 295，是一局很长的游戏
- 其余三名玩家均已破产（现金/存款全为 0）
- `currentPlayer = 0` 指向一名已出局的玩家，状态处于结束态

推断：阿土伯的资产是在**最后一次日推进之后**才因收取巨额过路费
（并同时令三人破产）而暴涨的，而下一次日推进再未发生，
故指数停留在暴涨前的 5。

**★ 2026-09 补充：机制已查清，解释站得住了。**

用 `tools/disasm.py` 的字节锚定命令重查，拿到三个此前没有的事实：

1. **更新函数是 VA 0x00423acf**（rich4-re 记的 0x00423ad0 差一字节），
   其**唯一运行时写入点是 VA 0x00423b1b**，由回合推进处 VA 0x0041cfbf 调用。
   另两处写入是开局置 1（0x004073b4）与读档还原（0x0044889c）。
   ——即物价指数**只在回合边界采样**，这一条现在是数出来的，不是推测的。

2. **除数确实是开局资金**。开局时 `mov eax, [eax*4 + 0x46cb94]` →
   `mov [0x49908c], eax`，表内恰好 6 档：
   `300000 / 200000 / 100000 / 50000 / 30000 / 10000`。
   这同时说明**开局资金选项就是难度旋钮**——选得越少，通胀越快。
   （已登记为 `rules/setup.ts` 的 `GAME_INITIAL_FUNDS`。）

3. **出局者被排除在平均之外**（`cmp byte [+0x15], 0 / je skip`）。

第 3 条是解开疑点的关键：**「按存档状态套公式得 11」这个算法本身就用错了
样本**。它只按终局时唯一存活的阿土伯算，而**最后一次真实采样发生在其余三人
尚未出局时**——那时分母是 4、分子还摊进了三个穷人，平均自然低得多。
把三人算作在场重算，结果正落在 5 这一档。

所以：**存档里的 5 是对的，拿终局状态套公式才是错的。**
`rules/wealth.test.ts` 里加了一个用例把这个机制显式钉住。

⚠️ 仍未做的事：没有用原版实机复现「破产当日资产暴涨」的过程。
上面是**基于反汇编的结构性解释加数值自洽**，不是实机验证。
代码按 SAVE1 已验证的公式实现，不做任何迁就 Save0 的特殊处理。

## 逆向源自身的错误（本项目已按汇编校正）

### E-001：`csrc/fortune.c` 的 case 15 转录错误

`rich4-re/csrc/fortune.c` 的 `fortune_check()` 中：

```c
case 15:
    ch = players[current_player].traffic_method;
    if (ch > 2) return 0;
    if (ch == 0) { *v = 15; }        // ← 映射到自己
    else if (ch == 2) { *v = 16; }
    return 1;
```

这破坏了 14/15/16 三个事件的对称性：

| case | traffic=0 | traffic=1 | traffic=2 |
|---|---|---|---|
| 14 | 不变(14) | → 15 | → 16 |
| 15 | **C 版写 → 15** | 不变(15) | → 16 |
| 16 | → 14 | → 15 | 不变(16) |

按 14 与 16 的规律，case 15 在 `traffic == 0` 时应映射到 **14**。

**汇编证据**（`rich4.asm` `loc_0044bdd1`，即 case 15 的分支）：

```asm
loc_0044bdd1:
mov  ch, byte [eax + (_rich4_all_players_state + 17)]   ; traffic_method
cmp  ch, 2
ja   short loc_0044be0d                                  ; > 2 → 不可行
test ch, ch
jne  short loc_0044bde8
loc_0044bde0:
mov  dword [edx], 0xe                                    ; ★ *v = 14，不是 15
```

另一佐证：整个 `fcn_0044bb4b` 中对 `[edx]` 的写入**只有 7 条指令**
（`0xa, 0xb, 0xc, 0xd, 0xe, 0xf, 0x10`），而 C 版在 case 14/15/16 里写了 6 处，
说明这三个 case 在汇编中共用同一组写入路径。

**统一规律**：
```
case 14/15/16:
    if (traffic_method > 2) return 不可行;
    eventId = 14 + traffic_method;
```

**处置**：本项目按**汇编**实现（`packages/core/src/events/fortune.ts`），
并有专门测试 `case 15 + traffic=0 映射到 14` 固化。

> 建议后续向上游 `rich4-re` 反馈此转录错误（DEVELOPMENT_PLAN.md R6）。

### Q-002：购地卡的敌意更新是空操作（原版 bug）

原版 VA 0x004423c4 计算了一个浮点敌意值：

```asm
ecx = land_price * price_index
fild  dword [esp]              ; ecx
fild  word  [esp + 4]          ; level
fadd  dword [0x46531c]         ; + 2.0
fdiv  dword [0x465320]         ; / 5.0
fmulp st(1)                    ; → land_price × pi × (level + 2) / 5
sub   esp, 8
fstp  qword [esp]              ; ★ 压入 8 字节 double
push  edx / push esi
call  0x40df69                 ; update_hostility
add   esp, 0x10                ; 清理 16 字节
```

但 `update_hostility`（VA 0x0040df69）的序言是 `push ebx; push edi`，
其第三个参数取自 `[esp + 0x14]`，是 **4 字节 int**：

```asm
0040df69  push ebx
0040df6a  push edi
0040df6b  mov  edx, dword [esp + 0xc]    ; arg0 victim
0040df6f  mov  ebx, dword [esp + 0x10]   ; arg1 from
0040df97  mov  ecx, dword [esp + 0x14]   ; arg2 delta ← 4 字节
```

对比均富卡的调用现场，它压的是 `push eax`（int），完全吻合。
而购地卡压了 double，被调方读到的是**其低 32 位**。

**实测**：在 840 种真实参数组合下（地价 1000~8000、物价指数 1~20、
等级 0~5），该低 32 位**无一例外为 0**——因为这些结果都是低位为零的
"整齐"浮点数。

**处置**：按 C-FID-4 原样保留，本实现同样不产生敌意。
原版意图公式记录在 `packages/core/src/cards/buy-land.ts` 的
`intendedBuyLandHostility`，并有测试固化「低 32 位恒为 0」这一事实。

### Q-FAC-1：设施的 `type` 在地图数据里恒为 0

过路费按 `facility.type`（+0x18）分三路（见 `rules/facility.ts`），

候选线索：`+0x1b` 在地图数据里**有值且因设施而异**（观察到 1 / 4 / 7），
但尚未找到它与 `type` 的关系。

### 监狱／医院：已定位的结构（尚未实现）

两者结构**完全对称**，偏移相差约 0xF30，可以对照着做。

| | 监狱 | 医院 |
|---|---|---|
| 计数字段 | `+0x34` | `+0x35` |
| 落点处理入口 | `0x0043d304` | `0x0043e9a4` |
| 释放函数 | `0x0043d7bf` | `0x0043ee6e` |

**已确认的规则片段**

- 刑期**由调用方以参数传入**（`[esp+0x18]`），不是常量。
  - 新判：`counter = days`（VA 0x0043d65d）
  - 加刑：`counter = (existing + days) & 0x7f`（VA 0x0043d6c5..0x0043d6d0）
    ★ 末尾的 `and ch, 0x7f` 是为了防止加法进位误置「待释放」位——
    这反过来印证了 0x80 是状态位而非计数的一部分。
- 释放函数对**玩家**（索引 < 4）走 `call 0x0040d6be` 并清空
  `byte [idx + 0x496b30]`；索引 >= 4 是地图上的物件／NPC，另走一套
  （表在 `0x498e28`，步长 0x10）。
- `0x496b30` 是一张 **8 项的字节表**，落点处理开头有
  `for (i=0; i<8; i++) if (!table[i]) break;`——看形状是牢房／病床占用表，
  满员（i==8）时直接返回，**语义待确认**。

**尚未做的**：两个入口函数体内混着大量图素加载（`0x450441`）与对话框，

### 開局自帶載具已实现

需求方提到「可以选择开局时全局自带载具（汽车/机车）」，这正是
`jump.mkf` 每个角色有三套侧视动画的原因。回汇编查实：

```asm
; VA 0x00407219 —— 开局逐个玩家
dl = byte [0x46cb44]                  ; ★ 全局设置：0 走路 / 1 機車 / 2 汽車
[player + 0x11] = dl                  ; traffic_method
if (dl != 0) byte[0x497323 + dl]--    ; 扣那件交通工具的全局库存
dl = byte[0x46cb44] + 1
[player + 0x12] = dl                  ; ★ ndices = traffic + 1
```

### ~~Q-GND-2 / Q-GND-3~~：底图格式已完全解出（**已结案**）

这两条都是**误判**，源头是同一个错误的前提。记在这里作为方法论教训。

当时的推理：文件长 5319312，减去 16 字节头与 512 字节调色板，
余下恰好能被 5184 整除得 **1026**，于是认定「每块 1026 字节」。
在这个前提下怎么摆都摆不对，于是又派生出两个问题：
多出的 2 字节在块首还是块尾（Q-GND-2）、块该怎么摆（Q-GND-3）。

真相来自原版地图加载代码 VA 0x00407b66：
```asm
memcpy(0x48b6b4, ground + 0x10, 0x200)   ; 调色板
[0x48bac4] = ground + 0x210              ; ★ 块排布表
[0x48bacc] = ground + 0x2a90             ; ★ 像素数据
```
`0x2a90 − 0x210 = 10368 = 5184 × 2`。即：

- `0x210` 起是 **5184 项 u16 的块排布表**（0..5183 的一个排列）
- `0x2a90` 起才是像素，**每块 1024 字节**，共 5308416 = 2304²

**根本没有「每块 1026 字节」这回事**——1026 = 1024 + 2 是把两张表
当成了一条记录。块间那圈 32 像素错位，就是排布表没被用上的后果。

★ 教训：**能整除不等于是记录长度**。症状（字母被切开、接缝 16.4
对块内 9.3）早就看见了，却一直在「这些块该怎么摆」的框架里找答案，
没有回头质疑「块到底是不是 1026 字节」。
解开它的是去 exe 里读加载代码——**一次反汇编胜过十次统计拟合**。

### Q-MUSIC-1：配乐的**音色**不是原版的

原版的 25 首配乐是磁盘上的标准 .mid（顺序见游戏目录的 `Midi.txt`）。
本项目自带 SMF 解析（`assets-pipeline/midi.ts`，格式 0/1、变长量、
running status、tempo 变化全覆盖，25 首全部解得开）与一个 WebAudio
合成器（`client/music.ts`）。

**旋律、节奏、时值是数据，做到了精确；音色做不到。**
听起来什么样取决于当年那块声卡的 GM 波表——同一份 .mid 在不同机器上
本来就不一样，没有一个「原版音色」可供比对。合成器按 GM 大类
（钢琴/风琴/贝斯/弦乐/铜管）粗分成几种波形，不假装是波表合成。

⚠️ **打击乐（9 号通道）整条跳过**：那个通道上的「音高」是鼓号不是音高，
用振荡器弹出来只会是一串怪叫。宁可没有鼓，也不要错的鼓。

要真还原，得另接一个 SoundFont 播放器并让用户自备音色库（.sf2）。
那属于步骤 2 的「画质/音质升级」，不是 1:1 移植的一部分。

### ~~魔法屋~~：两个转盘都已解出（**已结案**）

  直接拿去算罚金会算反。
- **搭档机制**：神明离场时，下标 0..11 的会换成**配对的另一个**登场

- **炸彈会传染**：引信没走完而同格有别人时，塞给**下标最小**的那位

### Q-OBJ-2：物件重新登场的落点挑法未完全解

`place_object` 的目标格由 `pick_object_node`（VA 0x0040aa6c）挑：

```asm
候选 = 所有满足 (flags & 0x80ffff00) == 0 且**可走**的节点
再抽: idx = rand() % 候选数
if (传了参照节点) {
    if (|x − 参照x| < 300 || |y − 参照y| < 300) goto 再抽   ; ★ 必须离得够远
}
```

本引擎实现了无参照的那一半（开局投放）。**带参照的重抽没有接**——
神明被送走后，搭档在本引擎里只抽一次，可能落在原地附近。
后果仅限位置观感，数量与种类都是对的；但**随机数消耗与原版不同**，
故不能拿来与原版存档逐帧对齐。

另外原版筛候选查的是节点 flags 的**运行时**占用位；本引擎不在节点上
镜像那份状态，改为反查物件表，效果等价。

五个共用一张表 `_rich4_all_special_players_state` @ **0x498e28**，
步长 16、**下标 = actor − 4**，五项正好 80 字节：

```c
struct special_player {   // 16 字节
  uint16 x, y;            // +0  +2
  uint16 node_id;         // +4   ← 落点处理就是从这里取格子
  uint16 last_node_id;    // +6
  uint8  owner;           // +8   ★ 主人
  uint8  direction;       // +9
  uint8  f10, state;      // +10 +11
  uint8  f12_13[2];       // +12..13
  uint8  halted;          // +14  非 0 → 收场
  uint8  single_step;     // +15  非 0 → 只走一步
};
```

**⚠️ 本条先前写错两处，已按 exe 改正：**

1. 「`[0x498dec]` 步长 16」——`0x498dec` 是**把 actor（不是 actor−4）乘 16**
   之后的基址：`0x498dec + actor*16 == 0x498e28 + (actor−4)*16`，同一张表。
2. **「`+4` 记着主人是谁」是错的 —— `+4` 是 `node_id`，`+8` 才是主人。**
   证据：VA 0x0041b472 取出 `[actor*16 + 0x498dec]` 后立刻拿它去查节点表。
3. 「8 = 飞行物」——**8 就是機器娃娃**。它被 `[0x49910c] = 8`
   （VA 0x00446b94，道具 1 的使用处理）设上去，记录写在表的第 4 项
   `0x498e68 = 0x498e28 + 4*16`。

**已实现的两条走子规则**（都从 `0x0040dd1f` 的行动者分派里解出）：

- **機器娃娃固定走 9 步**，不掷骰子（0x0040deb9 `mov esi, 9`）。
  沿途**见物件就轰走**：落点处理 VA 0x0041b4e7 在种类跳表**之前**
  就把 actor 8 截住，`0x40fafd` 算一个「打飞」的速度向量、`0x40e14d` 释放物件，
  然后**直接收场**。所以娃娃不吃禮物、不中地雷、不被神明附身、
  也不会被路障拦下 —— 它就是一台清道夫。
- **NPC 走 `rand() % 9 + 2` 步（2..10）**，用的是裸 `rand()` 不是骰子
  （0x0040de50）。出獄时 `last_node = 0`，故**第一步四个方向都能走**。

### ★ 四个 NPC 的安置与惡犬（**需求方指出，已回 exe 证实并实现**）

先前本文件默认「四个 NPC 都在監獄」，**错的**。需求方指出兩個蹲監獄、

**① 开局是 2 + 2，而且连是哪两个都写死了**

```asm
0040731b  memcpy(0x498e28, 0x47ecec, 0x50)   ; 五个替身记录的初值
0040732d  memset(0x496b30, 0, 8)             ; 監獄占用表清零
0040733e  memset(0x496b60, 0, 8)             ; 醫院占用表清零
0040734f  dh = 1
00407351  [0x496b34] = dh                    ; 監獄槽 4 = 小偷
00407357  [0x496b35] = dh                    ; 監獄槽 5 = 強盜
0040735d  [0x496b66] = dh                    ; 醫院槽 6 = 流氓
00407363  [0x496b67] = dh                    ; 醫院槽 7 = 間諜
```

初值表 `0x47ecec` 的 80 字节 dump 出来，除 `+10` 外**全是 0**，
`+10` 依次是 **1 / 1 / 2 / 2 / 3** —— 与上面四条严丝合缝。
由此定死 **`+10` = 去处：0 在场 / 1 監獄 / 2 醫院 / 3 未出场**
（另两条独立证据：送進監獄 0x0043d71f 写 1、送進醫院 0x0043ee37 写 2、
保釋出獄 0x0043d7f0 写 0）。

⚠️ `node_id` 初值是 0 —— **关着的人不在棋盘上**，保釋时才从
監獄/醫院那一格起步。

**② 惡犬咬 NPC → 進醫院**

玩家与 NPC 走的是**同一段代码**，只在「说台词」那一小段分岔：

```asm
0041b837  ; 惡犬
0041b83d  if ([0x48baf8] != 0) goto 结束   ; 没停下来就不咬
0041b847  release_object(0xb)               ; 狗自己消失
0041b855  if (actor >= 4) goto 0x41b8a7     ; NPC 跳过台词
0041b8a7  ; ★ 合流
0041b8e0  [0x48baf8] = 0                    ; 剩余步数清零
0041b8e6  send_to_hospital(actor, 3)        ; ★ 对 NPC 同样调用
```

`send_to_hospital` 的 NPC 分支（0x0043ee0f）：`if (actor >= 8) return`
（**機器娃娃咬不着**）→ 清节点占用位 → `[+10] = 2` → `[+11..15] = 0`

主人记成**保釋他的人**，`last_node = 0`（第一步四个方向都能走），

| 回老家 | 再踩到監獄(4)/醫院(5) | 見下 | ✅ |
| 取過路費 | 間諜 踩别人地產/設施 | 地块 `+0x2c` / 設施 `+0x30` = **上一笔**（mov 不是 add）| ✅ `landLastToll`/`facilityLastToll` |
| 取盈餘 | 間諜 踩别人上市企業 | 企業 `+0x28`，**可为负** | ⬜ **缺字段** |

**★ 与需求方口述不一致的两处，本引擎按 exe 走**

1. **搶銀行是两成不是一半。** `fmul qword [0x463b60]`（0x0041c37d），
   那 8 个字节 dump 出来是 IEEE-754 的 **0.2**。
2. **奪卡不是強盜专属。** 判据是 `cmp [0x49910c], 4 / jne 奪卡`（0x0041c201），
   所以 強盜／流氓／間諜 三个都会顺手抽走同格玩家一张牌。
   另外**保護費同样 `pay_money(地主, 主人, …)`** —— 需求方说「不会直接交给
   保释人」与 exe 不符。

★ 另有一处口述与 exe 的小差：需求方说四大惡人「每次随机前进 1～10 格」，
exe 是 `rand() % 9 + 2`（0x0040de50），即 **2～10**。以 exe 为准。

**★ 「流氓的保護費与地产价值有关，具体查代码」—— 查到了**

那条循环里有一句 `strcmp(esi + 4, ebp + 4)`（0x0041c514）：**地块名相同才算数**。
原版的地块名是**按地区重复**的（一片地区好几格同名），所以保護費不是按落点
那一格算，而是**把地主在这一整片地区的地價全加起来**再乘物價指數。

**★ 回監獄／回醫院的机制**

`+11` 低 7 位记着**他是哪儿出来的**（1 監獄 / 2 醫院），bit7 是
**「已经离开过那一格」**：

```asm
0041c7ba  if ((+11 & 0x7f) == 1 && 这格 specialKind == 4) {   ; 監獄
0041c7d2    if (+11 & 0x80) send_to_prison(actor, 0)           ; ★ 回去蹲着
0041c7e9    else            +11 |= 0x80                        ; 第一次只做标记
          }
0041c80a  醫院那一路同构（== 2、specialKind == 5、send_to_hospital）
```

保釋时写 `+11 = 1`（或 2），而且人此刻就站在監獄/醫院格上，
所以 0x80 当场就置上了（0x0043d84e）——**下一次踩到就回去**。

**★ 走子循环已接线**（`rules/npc-walk.ts`）

保釋当场就把人放上路，整趟**同步走完** —— 原版把 `[0x49910c]` 切成 4..7，
走完再切回玩家，期间没有任何玩家输入，所以对 core 来说这就是一个动作
（与機器娃娃同理）。落点按上表逐格结算，踩到老家即刻收场。

顺带钉死一处容易漏的差别：**钱进哪个口不一样**。
`pay_money` 第四个参数的 bit0 就是 `PAY_FLAG_CREDIT_TO_CASH`：
搶銀行是 `push 5`（0x0041c38f）→ **進現金**；
保護費与間諜那两条是 `push 0`（0x0041c576 / 0x0041c780）→ **進存款**。

**★ 还缺什么**

1. **間諜取過路費已接**（写入点找到了：住宅 0x0041a00b、設施 0x0041a75e，
   都是 `mov [+0x2c / +0x30], 實付` —— 记的是**上一笔**不是累计；取完不清零，
   同一块地能反复取，照抄）。**取盈餘仍缺**：企業 `+0x28` = 累積盈餘，有符号，
   负数时 `pay_money` 自然反向（「公司亏损时保釋人替企業主掏钱」）。
   ✅ 2026-09-14 随 P0-15 接上：`companyFunds[]` 就是 +0x28，负数反向转账。
2. **控制类卡片道具对他们生效**（停留卡/轉向卡/烏龜卡…）以及
   **魔法屋针对男性的效果不影响他们** —— 两条都还没查。
3. **AI 不会保釋他们出来玩**：`decideBail` 走的是原版那条
   「一半概率不管 + 按個性挑」的路，能挑到 NPC；但**真人这边没有 UI**
   把这四个人列出来（属 M4）。

### ~~岔路口选方向~~：原版根本没有这个交互（**已修正的自创玩法**）

本引擎先前在 `nextCandidates` 返回多个候选时停成 `awaitingDirection`，弹框
问玩家走哪边。**原版没有这一步**：

```asm
; 走子选下一格 VA 0x0040c12c
mov  ecx, 0x40000000                  ; 掩码 bit30，每试一个槽右移一位
0040c14e  mov dx, [ebx + edx*2 + 0x18]        ; node.adjacent[i]（4 个槽）
0040c159  je  下一个                           ; 槽为 0 → 跳过
0040c16b  cmp edx, edi / je 下一个             ; ★ 等于 last_node_id → 跳过（不走回头路）
0040c16f  test [esp+0x24], ecx / jne 下一个    ; ★ 该槽被封 → 跳过
0040c17c  test esi, esi / jne 有候选
0040c180  next = player.last_node_id           ; ★ 一个都不剩 → 原路返回
0040c196  call rand / idiv esi                 ; ★ 有候选 → 随机挑一个
```

所以棋子是**一路向前**的：环形路段上「不走回头路」这一条就把方向定死了，
只有真正的支线口才会出现多个候选，而那时也是**引擎随机决定**，不问玩家。
玩家想改方向得靠卡（「向後轉」把 node 与 last_node 对调）。

两个顺带解出来的东西：

- **封路位**：节点 flags 的 bit 30−i 表示第 i 个邻接槽不通。八张地图上一共
  只置了 10 次，且全在岔路节点上。台湾图（地图 0）两个岔路各封掉一条，
  于是那两处实际只剩一条路——这正是「感觉上从来不用选方向」的原因。
  ⚠️ 这几位按**原始槽号**存，所以 `MapNode` 新增了 `adjacentSlots`
  （剔零后的 `adjacent` 下标对不上）。
- **朝向**：`player +0x10` 是一个 0..7 的方向，每走一步由位移算出来
  （`0x00454fb4` 是定点 atan2 + 八分圆量化 + 一张 `[2,3,4,5,6,7,0,1]` 的重映射表）。

### Q-CHAR-1：棋子那 21 个资源只认了 2 个

棋子不在 `Panel.mkf`，在 **`Data.mkf` 的 `128 + 21 × 角色`**：

```asm
0040b954  mov al, byte [player + 0x13]   ; character
0040b95c  edi = edi*4 + al ; ×5

0040b966  add edi, 0x80                  ; ★ 资源号 = 128 + 21c
```

```asm
00408822  dl = player.direction
0040882d  ecx = 8 - [0x499088] ; ★ 减去当前视角旋转

00408849  add al, ch           ; + 当前帧
```

| 9..12 | 8/16/32/40 | 工程車 |

### 時光機（道具 10）已实现

原版是**靠还原快照**做撤销的，不是逐项回退：回合开始时给真人存一份整局
快照（`[0x48cb80 + 玩家 × 0x2718]`，@source VA 0x004480a0 `test byte
[player + 0x15], 1`），用道具时整块拷回来（VA 0x00448544）。

本引擎照此实现（`rules/time-machine.ts`），两处细节照抄：

- **PRNG 不在被拷回的那几块里**，所以退回去重掷骰子点数会变 —— 这正是
  这道具的用处。
- **还原失败（没快照）时不消耗道具**（`test eax, eax / je`）。托管中的
  玩家因此用不了它：快照只给 `who_plays == 1` 存。

另外本引擎多守了一条：**快照本身不回滚**。否则「已经用掉一个時光機」
这件事也会被撤销，等于无限后悔。

### Q-AI-2：AI 的「個性闸门」—— 表解出来了（2026-09-14）

`0x47fdf1` **不是一张独立的表**，它是 `card_table`(0x47fdea) **偏 7 字节**：
`[0x47fdf1 + action×8]` 读的是 `card_table[action].f7`。跳表 `0x475324` 共 43 项 =
**30 张卡 + 13 件道具**（道具表 0x47fee2 紧接卡片表，f7 同位，action 31..43 → 道具 1..13）。
即整条闸门就是：**f7 = 凶狠度 0..2**，`f7 − 個性 ≥ 2` 从不、`== 1` 1/3 概率、`≤ 0` 照做。
乖寶寶只随手打 f7=0 的牌，大老奸什么都打。卡片的 f7（§7.1 那一列）由此定名，
道具那侧上一轮已在公佈欄挂牌里见过同一条。**Q4 结案一半（f6 仍未解）。**
**已接线（2026-09-14）**：`ai/personality.ts::personalityAllows` + `policy.ts` 的 `gated/gatedTool`，
那次 `rand()%3` 的替身记 D-004。下面是原先的记录：

原版每个 AI 行为在动手前都要先过一道**個性闸门**（`+0x17`，
`0 乖寶寶 / 1 普通人 / 2 大老奸`；这三个名字取自原版「託管AI」对话框的
实机截图，见 `original-screens.md` 的 S3）：

```asm
0041e69e  ; gate(action)
0041e6a4  edx = [0x47fdf1 + action*8]                ; 该行为「所需个性」
0041e6b2  eax = 當前玩家.+0x17                        ; 自己的个性
0041e6bd  edx -= eax
0041e6c1  if (edx >= 2) return 0                      ; 差两档以上：从不做
0041e6c9  if (edx == 1 && rand() % 3 != 0) return 0    ; 差一档：1/3 概率做
```

**没做的**：行为表 `0x47fdf1`（步长 8，每项第 0 字节是所需个性，

表长也未确定。

（`rules/visit.ts` 的 `BAIL_STYLE`，@source 0x0043d3ee / 0x0043ea9a）。
这是**以偏概全**——先前该字段甚至就叫 `bailStyle`，已改名为 `personality`。
其余所有 AI 行为目前**不过这道闸**，因此「乖寶寶」和「大老奸」在本引擎里

`0x475324` 这张跳表多半就是 `rich4_ai_use_card.asm` / `rich4_ai_use_tool.asm`
那两大段的调度入口，翻译它应与那两块一起做。

### 特別融資（銀行董事長专属）已实现

先前玩家结构里的 `specialFinance`(+0x28) 只是个摆设 —— 它**不是谁都能用的**。
需求方指出「窗户里的人只有当玩家是銀行董事長时才看得见」，回汇编查实了整套规则：

**谁是董事長**（@source VA 0x00436b1e）：扫上市企業表，找**行業別 == 7** 的那家，
它的 `owner` 就是董事長。八张地图上行業別 7 的企業各有一家，股票索引恒为 0：
中國信託・上海銀行・富士銀行・花旗銀行・行星銀行・聚寶銀樓・黃金銀行・假期銀行。
企業的 `owner` 由持股最多者决定，所以等价于「持有銀行股票最多的人」。

★ 顺带解出 `commercial + 0x1a` 是**行業別**（先前没解析这个字节）：
1 航空、2 飯店、3 電子、4 保險、5 汽車、6 石油、**7 銀行**、10 百貨、11 建設、12 門派。
只有 7 这一条是从 exe 读到的，其余按名字归纳。

**額度**（@source VA 0x00434593）= **除自己以外所有人的存款之和**，
即界面上那行「客戶存款總額」。

**借**（0x00434665）进 `money_in_bank` 与 `special_finance`，**不进 `loan`** ——
所以借款 90 天到期、拒絕往來那一套对它统统不适用，是**两笔账**。
**還**（0x004346bb）先扣存款、不够动现金；都不够就退「您的現金不足」，什么也不改。

**銀行資金準備不足**（@source VA 0x00436b5c）：取款之后立刻查一次
（0x0043784d `push 1`），若其他在场玩家的存款总额跌破董事長的已融資额，
弹「銀行資金準備\n\n不足%d元\n\n由經營者%s墊付！」并从董事長身上扣差额 ——
存款不够动现金，再不够就**破產**（0x00433bd8 末尾调破產）。

⚠️ 两处求和**口径不一致**，照抄不改：算額度那处 `i < 4` 不查在场与否
（破产者的存款也算进額度），強制墊付那处查 `who_plays != 0`。

### 公佈欄（玩家之间的二级市场）已实现

需求方提到「公佈欄是玩家或 NPC 可以把自己的卡片道具地產等挂上去出售的」——
这是引擎里**先前完全没有**的一整套机制。顺着这条线索从汇编解出来了：

**槽位**（@source 撤件 VA 0x004247d5）：每个玩家 `0x54 = 84` 字节、每槽 12 字节，
即 **7 个槽**。撤件是 `memmove` 把后面的往前挪、最后一格 `memset` 清零。
「板满」的判定就是看最后那一格（`cmp byte [player*0x54 + 0x496828], 0`，
`0x496828 = 0x4967e0 + 0x48`）。

**槽的结构**（@source 挂牌 VA 0x004246c5）：
```
+0  u8   類型（0 = 空）    +1  u8  挂牌时清零，用途未解
+2  u16  物品编号          +4  u32 標價
+8  u32  只有類型 1 用（股票的股數）
```

**四种類型**，由购买那一路的四路跳表 `0x004255ca` 逐条解出：

| 類型 | 是什么 | 编号 | 上限 |
|---|---|---|---|
| 1 | 股票 | 股票下标 | 无 |
| 2 | 地產／設施 | `< 4000` 是住宅地 `id−2000`，否则設施 `id−4000` | 无 |
| 3 | 道具 | 道具编号 | 买家该道具 ≥ 9 → 「道具欄已滿」 |
| 4 | 卡片 | 卡片编号 | 买家手牌 ≥ 15 → 「卡片欄已滿」 |

類型 2 的编码与傳送機那套是同一套。

**成交**（@source VA 0x004255e9）：先查现金（不够就「您的現金不足！」且不成交），
再按類型转移，最后 `pay_money(買家, 賣家, 標價, 0)` —— **付的是现金**。

**挂牌价**：AI 挂卡片用 `標價 × 100 × 物價指數`（@source VA 0x00428935）。
真人是自己输入（「請輸入欲拍賣的價格（市價：%d元）」）。
