### 7.106 ★ 第 123 条（本轮）：投注屏 WndProc 的卡点**量到字节级** —— `ret 0x10` 前 ESP 多弹了 0x104

第 122 条把 `0x42f7fc` 的驱动卡在「建屏那条走完 `ret 0x10` 时返回地址变 0」。
本轮把它**量化**（都是实测，不是推断）：

```
; 在 0x42f92d（`ret 0x10`）上 hook
ret 前的 ESP = 0x53fec0   → [ESP] = 0，[ESP+4..0x10] 全 0
按 ABI 应当在 ESP = 0x53ffc4（0x53fff0 是返回地址槽）
⇒ ★ 栈指针多弹了 0x104 字节（≈ 65 个 dword）
```

逐指令筛「弹栈 ≥ 8 字节」的点，只看到尾部那三处**正常**的
（`0x42f91a add esp,4` + `0x402460 ret` 合计 16、`0x42f929 add esp,0x5c`、
`ret 0x10` 自身 16）⇒ **漂移发生在被桩掉的深层调用里**
（`call()` 每次都会重置 ESP，所以只有往返计数能看出来）。

**下一步（已写进工作稿）**：把 `0x42f32c` 那类桩换成带 `pushad/popad` 的显式桩
逐个排除；或记录**每一次 ESP 变化**、找第一次与 ABI 不符的那条。

#### ★ 补：更可能的根因是**帧口径差 0x2c**

本轮还发现：本稿用 `emu.call()` 建帧，而 `call()` 的参数基址由它的压栈序列决定
（实测在 `0x53fde4` 一带）；WndProc 序言是 `push×4 / sub esp,0x5c`，
它按 **`[esp+0x70]`** 读第一个实参 ⇒ **`call()` 的帧与 WndProc 的帧口径相差
0x2c（≈ 11 个 dword）**。这解释了那 0x104 漂移里的一部分，也解释了为什么
「把 `wParam` 设成与深度相等」之后**反而**在 `0x42fdb6` 读到未映射地址
（它开始按真实布局读帧内量了）。

⇒ 下一轮两条路：① 改用 `eval_block(0x42f7fc, ret 址)` + **手搓帧**
（与 `0x4198b9` 同一套手法）；② 或在 `emulate.py` 的 `call()` 里加一个
「参数基址」参数。**本轮到此为止，不把半通的东西塞进闸门。**
