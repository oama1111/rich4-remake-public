## D-T034-1（**照抄原版**，已定案）PASS 之后那一格显示「住宿中」

@source `0x407` 消息处理 VA `0x0043a426`：

```asm
mov word [eax + ref_0048c436], 1     ; 座位状态 = 1
or  word [ref_0048c4a4], 0x110
```

而显示那一支（VA `0x0043c624` 起）把状态当索引去查
`_player_state_strings[状态−1]`（`0x004464ea8` 起，逐条 dump =
住宿中 / 消失中 / 坐牢中 / 住院中 / 冬眠中 / 夢遊中 / 賣方）。
同一个 `1` 也是「住宿中」的号（入口 VA `0x43c152` 按 `player+0x32` 写 1）。

**所以原版在玩家按下 PASS 之后，那一格的字会变成「住宿中」。**
本屏照抄：`auctionPass()` 把座位标成 `passed`，`auctionSeatCode()` 把它映射回
**状态号 1**，渲染走同一条状态字分支（`AUCTION_PASSED_CODE = 1`）——
那一格既没有小人也没有现金，只剩「住宿中」三个字。

★ **定案（2026-09-15，headless Chrome + 真 dev server 实测）**：
按下 PASS 之后，0 号座位的确变成「住宿中」，画面看上去确实与其余三格的
「N元」不一样。但证据链完整（写状态 → 查表 → 画字三步在同一屏），
按铁律 §1/§3「搞不清的去汇编找答案、不许改良」，**保留原版行为**，不改成「ＰＡＳＳ」。
若中央最终判定这是原版的显示 bug 并要我们跟改，只需把
`AUCTION_PASSED_CODE` 从 `1` 改成别的号（或让渲染对 `passed` 单开一句）——
一行的事。**最好还是拿一张原版拍賣屏截图仲裁**（现有 13 张实机截图里没有这一屏）。

## ✅ D-T034-2（**前提被推翻** · 2026-09-16）拍賣屏**不受**「動畫過程」管辖

## D-T034-3（解不出）有等级的地块缩略图缺两个全局

@source 地块那一支 VA `0x0043bec7` 起：

```asm
cmp word [ref_004991b6], 0            ; ← 另一套建筑风格
jne ...                               ;    本引擎里没有对应物
...
movsx edx, word [ref_004991b8]        ; ← 地图号
```

- `[0x4991b8]` = **地图号**（`new_game.asm:3361` `mov al, byte [0x48a439] / dec eax`）。
  本引擎的 `GameState` 里**没有**这一项（`setup.mapId` 只在 `main.ts` 的闭包里），

  `[0x4991b8]×5 + 等级 + 0x73`、設施走 `ref_0043bdd1` 那张 5 路跳表

**要补的话**：把 `mapId` 塞进 `GameState`（一条独立的小改动），
再把 `0x4991b6` 的语义查清。图 `30..49` / `116..183` 都已解包，肉眼可比对。

## D-T034-5（**已撤销 2026-09-16**）心理价位里的 `rand()` 曾经换成派生种子

这一条**撤销**：原来的理由不成立，实现已改回按原版消费**全局**随机流。

**当初的说法**：「引擎里不能在这里动 `GameState.rngState`（那会让存档回放漂移、
联机两端对不上）」，于是用 `seed = rngState ^ (实体号+1)×0x9e3779b1` 派生一条
独立序列。

**为什么不成立**：开拍发生在 **reducer** 里，两端对同一串 action 跑同一个
reducer、消费同样的次数，就**不会**漂；而竞价屏只读 `pending.limits`、
从不重算（`client/auction-screen.ts`，全仓仅 `openAuction` 一处调用
`auctionAiLimits`）。所以「两端对不上」这个担心从一开始就没有对应的机制。

**实测的代价**：不推 `rngState` ⇒ 每开一场拍卖，之后所有随机事件
（命運/新聞/骰子/魔法屋）都比原版**错位**一次 —— 正是簇 C 那一类
「多掷/少掷一次」的同一类缺陷，只是位置在拍卖里。

**现在的做法**（`state/reduce.ts` 的 `startAuction`）：
用 `WatcomRng` 从 `state.rngState` 起算，把 `rand01` 交给
`auctionAiLimits`，算完把 `rng.getState()` 回写进 state。

**掷几次**（@source 建表循环 VA `0x0043c5d0..0x0043c680`，一条闸门都不能少）：

| 闸门 | @source | 后果 |
|---|---|---|
| 座位槽为空 | `0x43c5ea test ax,ax / je` | 不掷 |
| `whoPlays & 6 == 0`（真人） | `0x43c5fa test byte [player+0x15], 6 / je` | 不掷；该座位心理价位留 **0** |
| 座位状态 ≠ 0（卖家 7 / 出不起底价 8） | `0x43c603 cmp word [座+2],0 / jne` | 不掷 |
| 顺序 | `0x43c5d0` 循环 `ebx = 0..3` | **按玩家下标升序** |

每次调用 `fcn_00439f0d` 内部 `call rand` **两次**（入口 `0x439f1c` +
地块支 `0x43a015` / 設施支 `0x43a0fb` 二选一），故「N 个可出价的电脑座位
⇒ 恰好 2N 次」。

**仍然有意不建模的**：拍卖窗口**动画**里的 4 处 `rand`
（`0x43b5ff` `rand>>10`、`0x43b945` `rand>>11`、`0x43b9d6` `rand&7+1`、
`0x43baa7` `rand>>11`，周围全是贴图与 vtable 调用）—— 它们按**帧**触发，
本身就是时间相关的，无法在无头 core 里复现。故原版「开完一场带窗口动画的
拍卖之后」的全局序列**本质不可逐位复现**；确定性引擎只保证**规则相关**的
那部分消费（心理价位）与原版一致。同理，AI 出价档位的挑选
（`loc_0043b124` / `0x43b183`）经查**不含** `rand`，复刻的
`auctionAiRaise` 写成确定性的是忠实的。

## D-T034-6（**已实证核过**，不是偏离）「Q 版小人」就是黄色描边剪影

入口那一段（VA `0x0043c4f5`）画的是资源 26 的图 `0x4e + 角色号` = **78..89**。

**中央 2026-09-15 复核**：`assets-clean/Panel/0026_078.png` 确实是黄色剪影，
**不是解析错误**，保持即可。本轮又补了两条自己的实测：

1. 逐张数「近黑像素占比」：78..89 是 **79%~82%**，且黑全在**四周**

所以这一条**不是偏离**，也不再是未决项：实现按剪影（照抄图号），已核过。

## D-T034-7（有意偏离）挥锤动画取三帧；原版没有固定的「三帧」

卡片算法第 3 条写的是「挥锤动画：三帧循环」。查证后：
原版每一口出价播的是**当前出价者自己那份资源 `3×角色 + 0x1b`** 的
`0..nchunk−1` 帧（`0x48c4a4 >> 8` 是帧计数、`[资源+4]` = `nchunk`），
VA `0x0043a6d5`；每个角色 5 帧或 6 帧（`Panel.mkf` 资源 27 是 5 帧、60/62 是 7/8 帧），
**不是三帧**。另有一段动画走 `3×角色 + 0x1d`（VA `0x0043ab5a`），
以及拍賣官脸上的几处小图（`18/19`、`22`、`26/27`，VA `0x0043b637` / `0x0043b74c`）
按 `rand()` 抽。

本轮按卡片取 **3 帧**（`AUCTION_HAMMER_FRAMES = 3`，节拍 100ms），
只播「当前出价者那张」的前 3 帧。要 1:1 的话需要
`sprite()` 暴露资源的 `nchunk`（现在只能按 0 base 索引猜），
以及把 `3×角色+0x1d` 与拍賣官那几处小图一并接上。

## ★ Q-AUC-1 定案（2026-09-15）：竞价循环搬进 core，本屏只收集真人那一口

`docs/known-deviations.md` 的 Q-AUC-1（「拍賣卡挂出的拍賣，电脑那一手没有出价
逻辑」）这一轮修掉了，**实现位置与原先相反**，记在这里。

### 为什么不能只补屏

本屏原先自己跑整条循环（`auctionSeats` / `auctionRaise` / `auctionPass` /
`auctionFinished` / `auctionOutcome`），可它**只在有渲染层时存在**：

- `packages/server` 是**无头**跑 core 的（服务器权威）；
- `soak.test.ts` 也是**纯 core 4 个 AI** 连跑。

于是 `pending{auction}` 在无头环境里**永远答不掉** —— 服务器与 soak 都卡死。
（自然对局里其实碰不到：AI 只在「脚下是对手的 ≥3 级地产」时才肯出拍賣卡
（`ai/policy.ts` 的 `paimai`，@source 0x0041ef26），实测 300 回合抽不到一张。
缺口是真的，只是难撞。）

### 现在的分工

| 在哪 | 干什么 | @source |
|---|---|---|
| `rules/auction.ts` | 座位表、心理价位、挑档、压价、终局判据 | `0x00439f0d` / `0x43c110` / `0x43b124` / `0x43b183` / `0x43b295` |
| `state/reduce.ts` | `openAuction` 开拍建表；`auctionBid` 走**一口**，该收尾时自己落槌 | `0x0043c5d9` 建座位 / `0x407` 消息 / `loc_0043b295` |
| `ai/policy.ts` | `auctionNextBid()`：轮到的这一家出一口（电脑） | 刷新循环 `loc_0043c4f5` 一带 |
| `client/auction-screen.ts` | 只**收真人那一口**（七颗钮）＋把每一口演出来 | `0x201`/`0x202` → `0x407` |
| `main.ts` | `scheduleAi` 在 `pending.kind === 'auction'` 时不再打「无事可做」 | — |

一个 `auctionBid` action = 一口：校验（轮到你 / 没出过价 / 出得起）→ 改现价或
标 PASS → 按 `loc_0043b295` 复查 → 成交/流标就用既有的终局形状落槌。
`decidePending` 里那一支与屏上「电脑那一手」**共用同一个** `auctionNextBid`，
不存在两条循环。

### ★ 这一轮顺手推翻的两处 T-034 旧结论

1. **`__round_toward_zero` 不是「就近取偶」。**
   `0x00457dbc` 把 x87 控制字 `mov byte [esp+1], 0x1f`（清掉 RC 两位 = 11）
   再 `frndint` —— 那是**向零截断**。`auctionBasePrice` 与 `auctionAiLimit`
   里的两处取整因此从「就近取偶」改成 `Math.trunc`
   （影响：`1001 × 1.5 = 1501.5` → 1501 而不是 1502）。
   ⚠️ `rules/percentage.ts` 的同名函数仍按就近取偶实现，**那是另一个问题**
   （本卡不动它，已报给中央）。
2. **`loc_0043b183` 的档宽区间是 `[1000, 5000]`，且 room 越界时不改档。**
   `cmp 1000 / jle` 与 `cmp 5000 / jg` 这一对 ⇒ `room == 1000` 走 5000 档；
   `room > 5000` 时四个区间都不命中 → **档位原样保留**。原实现这两条都反了。

### 仍然没解出的

- `[0x48c4b1] == 1` 时把档位强制成 1（`0x43b219` 前面那一段）：
  **不知道 `0x48c4b1` 是什么状态**。本引擎按「不等 1」处理（即不强制）。
- 入口那条「AI 只发 PASS、真人才能按放棄」的分工：电脑那支的出口确实是
  按钮 0（PASS），`auctionBid` 的 `status: 'giveUp'` 只由真人的第 7 颗钮产生。
- 席位是「4 个」还是「所有在场者」：原版座位表硬编码 4 槽
  （`loc_0043b295` 里 `cmp ebx, 4`），本引擎按 `bidders` 长度来
  （最多 4 人，故等价）。
