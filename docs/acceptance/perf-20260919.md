## 2. 命令（可复现）

```bash
# 1) 起 dev server（另开终端）
pnpm dev                       # Vite ready，Local: http://localhost:5173/
# 2) 起采样器
cp tools/perf-browser.js /tmp/perf.js
B=~/.agents/skills/gstack/browse/dist/browse
$B goto "http://localhost:5173/?screen=game&humans=0&ai=4&map=0&seed=7"
$B eval /tmp/perf.js           # → "perf started"
sleep 300                      # 连跑 5 分钟
# 3) 收数据
$B js "globalThis.__perfStop = true"
$B eval /tmp/perf.js           # → 一行 JSON
```

★ 必须用 `browse eval <file>`；`browse js "$(cat …)"` 解析多行脚本会出问题
（与 `tools/soak-browser.js` 顶部记的是同一个坑）。

**口径**：帧间隔只统计相邻两次 `requestAnimationFrame` 之差（第一帧无前驱，不入样）；
「标题屏首帧」= `PerformancePaintTiming` 的 `first-contentful-paint`（脚本只能**加载后**注入，
取不到 FCP 时依次回落 `domContentLoadedEventEnd` → `loadEventEnd`，结果里带 `paintSource`）。

## 3. 结果

实测时长 **314.6 s（≈5.24 分钟）**，四家电脑确实一直在玩：`turnCount 0 → 85`、`day → 22`、
`phase = moving`（结束时仍在动）。

| 指标 | 实测 | 目标（C-PERF） | 判定 |
|---|---|---|---|
| 帧率（由均值反算） | **59.9 FPS** | 60 FPS | ✅ |
| 帧间隔均值 | **16.7 ms** | — | — |
| 帧间隔 p95 | **17.6 ms** | — | — |
| 帧间隔 p99 | **18.5 ms** | — | — |
| 帧间隔 > 33 ms 的帧 | **10 / 18,834 = 0.05%** | — | — |
| 最长帧间隔 | 116.7 ms（1 帧，疑与切屏/GC 同拍） | — | — |
| `usedJSHeapSize` 起止差 | **0 B**（32 次采样恒为 304,000,000） | 内存 < 1.5 GB | ✅（见下注） |
| `navigationStart → 标题屏首帧`（网页版） | **88 ms** | 冷启动 < 3 s | ✅（网页版） |

注 1：`performance.memory.usedJSHeapSize` 在**没有** `--enable-precise-memory-info` 时会被
Chromium 量化（5 分钟 32 次采样全部读到同一个整数 304,000,000 B）。所以「起止差 = 0」只能当
**没有明显泄漏的线索**，不是精确值；要精确值需要带 precise 标志起浏览器（gstack browse 没有
这个开关，已如实记在这里）。

注 2：>33 ms 的 10 帧分布在整段 5 分钟里（占比 0.05%），未出现连续掉帧。

## 4. 60 / 内存两条的对照结论

- **60 FPS：达标。** 均值 16.7 ms、p99 18.5 ms、掉帧率 0.05% —— 全程贴着垂直同步。
- **内存 < 1.5 GB：达标（线索级证据）。** 稳定态 304 MB，远低于 1.5 GB；但见注 1 的量化说明。

## 5. 冷启动（桌面包）

### 5.1 网页版

`navigationStart → first-contentful-paint = 88 ms`（同上表），`domInteractive 71.1 ms`、
`DOMContentLoaded 293 ms`、`load 293 ms`、`transferSize 3221 B`。

### 5.2 桌面包（`dist-macos/…试玩-20260918b.zip`）

测法（脚本 [`tools/coldstart-probe.py`](../tools/coldstart-probe.py)，本机 pyobjc 直查 WindowServer）：

1. `pkill -x rich4-desktop` → 等 2 s；
2. `t0` 记时 → `open "大富翁4 重制版.app"`；
3. 每 50 ms 用 `CGWindowListCopyWindowInfo` 查**该进程**的窗口，第一次看到即记 `t_window`；
4. 5 次取中位数。

| 第几次 | `open → 窗口出现`（秒） |
|---|---|
| 1 | 1.889（冷文件缓存，含首次解压后的读盘） |
| 2 | 0.377 |
| 3 | 0.411 |
| 4 | 0.380 |
| 5 | 0.436 |
| **中位数** | **0.411 s** |

⚠️ **「窗口出现」不等于「标题屏首帧」。** 本环境里**量不到**标题屏首帧：
`CGWindowListCreateImage` 拿到的窗口位图全是黑的（没有「屏幕录制」权限），
`osascript` 问 `System Events` 会卡在权限提示上（实测 60 s 超时）。
所以：

- **能给的下界**：`open → 窗口出现` 中位数 **0.41 s**（< 3 s，但这不是验收口径要求的那一段）；
- **缺的一段**：`窗口出现 → 标题屏画出来`（要装素材 + 起前端）。5 次实测里，`open` 之后
  1 s 内进程都已驻留、窗口都在，但**没有**可用的画面证据说明此刻标题屏已经画出来。
- 建议：需求方在真机上**秒表实测 5 次**（或给「屏幕录制 + 辅助功能」权限，我就能自动量）；
  在此之前**「冷启动 < 3 s」判为「未能取证」**，不要按达标算。

## 6. 结论

| 出口条件 | 结论 |
|---|---|
| 60 FPS | ✅ 达标（59.9 FPS，掉帧 0.05%） |
| 内存 < 1.5 GB | ✅ 达标（304 MB 稳定；证据为量化值，见注 1） |
| 冷启动 < 3 s（桌面包） | ⚠️ **未能取证**：`open → 窗口出现` 0.41 s，`窗口出现 → 标题屏首帧` 本环境量不到（权限）。网页版首帧 88 ms |
| 与原版录屏逐帧比对 < 2 帧 | 本任务不含（通道 3 已由需求方降级为可选） |

**不达标/未取证项不在这里优化**；「冷启动标题屏首帧」的取证方式已登记
[`docs/escalations.md`](../escalations.md) 的 `E-1`，等需求方给真机秒表数或权限。
