# 与原版的已知偏离

> DEVELOPMENT_PLAN.md §5.1 **C-FID-4** 规定：不得以"手感更好""更平衡"为由修改任何原版数值或规则。
> 本文件登记**所有**有意偏离，每条必须说明理由。凡未登记的差异一律视为 bug。

## D-001：随机数播种策略按模式区分

| | |
|---|---|
| **类别** | **单机：零偏离**（完整复刻原版）｜**联机：新增行为**（原版无联机，无对应物可偏离） |
| **影响** | 不影响任何概率分布 |
| **状态** | 已实施（`packages/core/src/rng/policy.ts`） |

> **修订记录（2026-09-13）**：本条最初的方案是「全局改为显式注入种子」，那会让单机
> 失去原版的"读档重开刷结果"。经复核，这是把**引擎确定性**与**存档策略**两件事
> 混为一谈了。拆开后两者可以同时满足，单机的偏离**完全消除**。见下方「最终方案」。

### 原版行为

原版全程序共 **3 处** `srand()` 调用，**全部**以 `GetTickCount()`（系统启动至今的毫秒数）为种子：

| 地址 | 位置 | 时机 |
|---|---|---|
| `0x0040170F` | `asm/rich4_initialize.asm:146` | 游戏启动，DirectDraw 初始化后 |
| `0x00402FA1` | `asm/rich4_save_files.asm:507` | **读档之后** |
| `0x0041D06E` | `asm/rich4_player_core_actions.asm:4830` | 回合/新一天推进时 |

因此：
- 原版存档**不保存 PRNG 状态**；读档后重新播种，所以"读档重开会刷出不同结果"是**原版的真实行为**。
- 每回合都会用挂钟重新播种，PRNG 序列在回合之间被打断。
- **原版对局本质上不可复现。**

### 最终方案

关键是把两件**本不相干**的事拆开：

| 关注点 | 要求 | 由谁决定 |
|---|---|---|
| **引擎确定性** | `reduce(state, action) → state` 必须是纯函数 | 引擎本身，两种模式**都成立** |
| **存档是否写入 PRNG 状态** | 决定能否"读档刷结果" | 存档**策略**，按模式取不同值 |

做法是把「重新播种」表达为 action 流中的**一条显式 action**，而非让引擎去读挂钟。
非确定性因此被捕获成 action 日志里的**数据**，引擎保持纯函数。

| | 单机 `SINGLE_PLAYER_POLICY` | 联机 `MULTIPLAYER_POLICY` |
|---|---|---|
| PRNG 算法 | 位级一致 | 位级一致 |
| 存档写入 PRNG 状态 | **否** | 是 |
| 重新播种时机 | 启动 / **读档后** / **每回合**（与原版三处 `srand` 逐点一致） | 仅开局一次 |
| 读档重开刷结果 | **可以**（原版行为） | 不适用 —— 联机没有"读档"这个动作 |
| 断线重连 | 不适用 | 服务器下发含 PRNG 状态的完整快照，属**重同步**而非读档 |

### 为什么单机算「零偏离」

单机模式下，播种时机与原版三处 `srand(GetTickCount())` **逐点对应**，存档同样不含
PRNG 状态，因此「读档重开刷结果」这一原版特性被**完整保留**。玩家可观测的行为与原版
没有任何差异，故不构成偏离。

### 为什么联机算「新增」而非「偏离」

原版**没有联机模式**，不存在可供偏离的原版行为。联机的确定性播种是全新设计，
用于满足 DEVELOPMENT_PLAN.md §5.2 **C-DET-4**（断线重连、反作弊、赛后回放）。
它不改变任何一条游戏规则或概率分布。

### 附带收益

因为 reseed 值被记入 action 日志，**单机局同样可以完整回放**——
调试、复盘、bug 复现都能用，而这是原版做不到的。

### 溯源

- 原版 PRNG：`Rich4/rich4.exe` VA `0x00456F2D`（反汇编原始二进制确认）
- 原版三处 `srand`：`0x0040170F`（启动）、`0x00402FA1`（读档后）、`0x0041D06E`（回合推进）
- 实现：`packages/core/src/rng/watcom.ts`、`packages/core/src/rng/policy.ts`
- 测试：`packages/core/src/rng/watcom.test.ts`、`packages/core/src/rng/policy.test.ts`
  （其中「读档重开能刷出不同结果」与「重连恢复后结果完全一致」各有专门用例）

## ⚠️ 陷阱记录（非偏离，但必须避免）

### T-001：不要沿用 rich4-re 的 `mscrt.ld` 随机数映射

`rich4-re/asm/mscrt.ld:15-16` 把原版的 CRT 随机数重定向到了 msvcrt：

```
PROVIDE(_libc_srand = _srand);
PROVIDE(_libc_rand  = _rand);
```

msvcrt 的 `rand()` 用的是乘数 `0x343FD`、增量 `0x269EC3`，与原版 Watcom 的
`0x41C64E6D` / `0x3039` **完全不同**。

**后果**：逆向项目构建出的 `rich4_mscrt.exe` 虽然能运行，但**随机序列已与原版不同**。
任何从该可执行文件观测到的随机行为都不可作为保真依据。

正确做法是以**原始 `rich4.exe` 的反汇编**为准，本项目已如此实施。

## 已查明的原版机制（非偏离，存档实证）

### F-001：开局资金分配

| 项 | 值 | 证据 |
|---|---|---|
| 初始资金 `_rich4_game_initial_fund` | **300,000** | `Save0.dat` 与 `SAVE1.DAT` 偏移 `0x268A` 均为 300000 |
| 开局现金 | `初始资金 × init_cash_ratio / 100` | 见下表 |
| 开局存款 | `初始资金 − 开局现金` | 同上 |

`SAVE1.DAT` 是一局刚开始的游戏，四名玩家的现金/存款拆分**精确匹配**各自角色的
`init_cash_ratio`（该字段来自 `rich4_characters.c`）：

| 玩家 | 角色 | 现金 / 存款 | 现金占比 | 角色的 `init_cash_ratio` |
|---|---|---|---|---|
| 1 | 孫小美 | 150,000 / 150,000 | 50% | **50** ✓ |
| 2 | 阿土伯 | 120,000 / 180,000 | 40% | **40** ✓ |
| 3 | 金貝貝 | 240,000 / 60,000 | 80% | **80** ✓ |
| 0 | 小丹尼 | 150,000 / 150,000 | 50% | 55（见下） |

玩家 0 是该存档的当前行动玩家，已经行动过；按 55% 开局应为 165,000 / 135,000，
现为 150,000 / 150,000，差额恰为一笔 15,000 的银行存入。故不构成反例。

> 这同时解答了 M1 阶段留下的疑问（「小丹尼 ratio=55 却是 50:50」）。

### F-002：物价指数的更新时机与公式

**公式**（`rich4_update_price_index.asm`）：
```
新指数 = (在场玩家总资产之和 ÷ 在场人数) ÷ 初始资金      // 两次均为 idiv，向零取整
if (新指数 > 当前指数) 当前指数 = 新指数                  // 只升不降
```
「在场」的判据是 `cmp byte [player+0x15], 0`，即 **who_plays 整个字节非 0**。

**调用时机**：全程序**仅一处**调用，位于日期推进函数 `fcn_0041cf67`
（`rich4_player_core_actions.asm:4761`），即**每推进一天**更新一次，
且被 `fcn_0041d89e() != 1` 门控。

**门控函数 `fcn_0041d89e`** 是胜负条件检查：
- `ref_0049911c`（推测：目标天数）与 `ref_00499108`（推测：目标金额）
  同时为 0 时直接返回 0，即无胜负限制、不阻断更新。
- 两个样本存档中这两个字段均为 0。

**实证**：`SAVE1.DAT` 新开局，唯一在场玩家总资产 300,000，
初始资金 300,000 → 指数 = 1，**与存档记录完全一致** ✓

**`Save0.dat` 的差异及解释**：该存档记录 `price_index = 5`，
但按公式推算应为 11（唯一在场玩家流动净值 3,320,222 ÷ 300,000）。

最合理的解释是**它是终局存档**：
- 天数计数 `ref_004990e4` = 295，是一局很长的游戏
- 其余三名玩家均已破产（现金/存款全为 0）
- `currentPlayer = 0` 指向一名已出局的玩家，状态处于结束态

推断：阿土伯的资产是在**最后一次日推进之后**才因收取巨额过路费
（并同时令三人破产）而暴涨的，而下一次日推进再未发生，
故指数停留在暴涨前的 5。

⚠️ 此解释**尚未证实**。若后续能用原版实机复现「破产当日资产暴涨」
的场景并观察指数，即可确认或推翻。在此之前，代码按已被 SAVE1 验证的
公式实现，不做任何迁就 Save0 的特殊处理。

## 逆向源自身的错误（本项目已按汇编校正）

### E-001：`csrc/fortune.c` 的 case 15 转录错误

`rich4-re/csrc/fortune.c` 的 `fortune_check()` 中：

```c
case 15:
    ch = players[current_player].traffic_method;
    if (ch > 2) return 0;
    if (ch == 0) { *v = 15; }        // ← 映射到自己
    else if (ch == 2) { *v = 16; }
    return 1;
```

这破坏了 14/15/16 三个事件的对称性：

| case | traffic=0 | traffic=1 | traffic=2 |
|---|---|---|---|
| 14 | 不变(14) | → 15 | → 16 |
| 15 | **C 版写 → 15** | 不变(15) | → 16 |
| 16 | → 14 | → 15 | 不变(16) |

按 14 与 16 的规律，case 15 在 `traffic == 0` 时应映射到 **14**。

**汇编证据**（`rich4.asm` `loc_0044bdd1`，即 case 15 的分支）：

```asm
loc_0044bdd1:
mov  ch, byte [eax + (_rich4_all_players_state + 17)]   ; traffic_method
cmp  ch, 2
ja   short loc_0044be0d                                  ; > 2 → 不可行
test ch, ch
jne  short loc_0044bde8
loc_0044bde0:
mov  dword [edx], 0xe                                    ; ★ *v = 14，不是 15
```

另一佐证：整个 `fcn_0044bb4b` 中对 `[edx]` 的写入**只有 7 条指令**
（`0xa, 0xb, 0xc, 0xd, 0xe, 0xf, 0x10`），而 C 版在 case 14/15/16 里写了 6 处，
说明这三个 case 在汇编中共用同一组写入路径。

**统一规律**：
```
case 14/15/16:
    if (traffic_method > 2) return 不可行;
    eventId = 14 + traffic_method;
```

**处置**：本项目按**汇编**实现（`packages/core/src/events/fortune.ts`），
并有专门测试 `case 15 + traffic=0 映射到 14` 固化。

> 建议后续向上游 `rich4-re` 反馈此转录错误（DEVELOPMENT_PLAN.md R6）。
