### 7.26 ★ 第 44 条（本轮）：「写了但没人调」审计 —— 揪出**破产清算漏了一整段**与**魔法屋拍賣空转**

第 42/43 条那套审计再换一个方向：不查「状态写了没人读」，改查
**「函数写了没人调」**（`tools/scratch/audit-uncalled.py`）。

口径很重要（第一版口径不对，看不出重点）：一个导出项若在**它自己的模块里**被调用，
那只是封装松；只有在**整个仓库里除声明行之外一次都不出现**，才是真的死代码。
死代码在 1:1 复刻里往往等于「原版有、我们写了壳却没接线」。

#### (1) ★★ 破产清算的**下線拍卖**整段缺失

`0x40cd87` 的后半段（`0x40d002` 起）此前**没人读过**，这一轮补上后发现的：

```asm
0040d1c6  cmp  esi, 3                ; esi = 被释放的实体数（地块 + 設施）
0040d1c9  jle  0x40d211             ; ★ ≤3 处：一场都不拍
0040d1cb  push 5 / call 0x4549cf     ; 显示提示（纯表现）
0040d1d5  xor  ebx, ebx             ; ebx = 已拍场次
0040d1d7  jmp  0x40d1f7
0040d1d9  push 0 / mov ax, dx / push eax
0040d1e1  push -1                    ; ★ 卖方 = -1 ⇒ 成交款进**公库**
0040d1e3  call 0x43bde5              ; 开拍（阻塞：整场跑完才返回）
0040d1ed  [esp + edi] = 0            ; 从候选表划掉
0040d1f1  inc ebx / cmp ebx, 3 / jge 0x40d211
0040d1f7  call rand / idiv esi       ; ★ rand() % 实体数
0040d206  mov dx, [esp + edi]
0040d20a  test dx, dx / je 0x40d1f7  ; 抽到空槽就**重抽**（消耗随机数）
0040d20f  jmp 0x40d1d9
```

三条要点：**只有 > 3 处才拍**、**只拍 3 场**（不是把释放的全拍了）、
地块与設施**共用一张候选表**；每抽一场划掉一处，重复抽到空槽要重新掷。

顺带把同段的另外两个循环也补上了（`docs/systems/bank.md` §4.4 新增）：
- 企業归属**无条件**清零（`0x40d10d..0x40d137`）：只看 `commercial+0x18 == 玩家+1`，
  **不看持股** —— 复刻先前只在「持股非空」时才重排，于是
  「挂着董事长名头却一股不剩」那种状态脱不了手；
- 地块 `+0x30` / 設施 `+0x34` 是**4 字节**地契到期日，两个都是 `mov dword, 0`。

**实现**：新增 `state.pendingQueue`（见 `state/types.ts` 那段注释）。
原版的 `0x43bde5` 是**阻塞调用**，同一流程里连开多场是正常的；复刻的拍卖是
**待决交互**（`pending`），一次只能挂一场，于是同一流程里的其余场次排队，
前一场落槌时自动接上（`startAuction` / `chainQueuedAuction`）。
⚠️ 没有这条队列时第二次 `startAuction` 会**直接覆盖**第一场 —— 竞价进度凭空消失。

#### (2) ★ 魔法屋「拍賣」结果此前是**空转**

`applyMagicRequest` 的 `case 'auction'` 就是一句 `return state` —— 转到「拍賣」
什么都不发生。**这一条规格里早就写了**（`rich4-spec/docs/systems/magic-house.md`
§5「拍賣當格土地」已给出 `編號 = 地圖格[c]+0x20`、（2000,6000）闸门与
「得標者向原主付款」），是**实现没跟上规格**，不是规格缺口。
原版那一段（`0x0043242b..0x004324d5`）：

```asm
0043242b  imul ebx, [0x49910c], 0x68          ; 当前行动者 = 本次中签者
00432432  cmp  dword [ebx + 0x496b9a], 0
00432439  jne  跳过                            ; +0x35 非 0 → 不拍
0043243f  mov  ax, word [ebx + 0x496b74]       ; 他所在的**节点号**
00432454  mov  bx, word [0x498e80 + ebx*8 + 0x20]   ; ★ 节点 +0x20 = 该格 type
0043245f  cmp  ebx, 0x7d0 / jle 跳过
00432471  cmp  ebx, 0x1770 / jge 跳过          ; 必须落在 (2000,6000) = 地产/設施
004324cc  push 1 / push ebx / push [0x49910c]
004324d5  call 0x43bde5                        ; ★ 卖方 = 该玩家自己
```

⇒ 拍的是**他脚下这一格的产业**（不是随机挑一块），款子归**他**。

#### (3) 顺带查清的 |连带的卡死

破产清算开的那几场拍卖，恰好落在「**破产者已经出局、却还是 `currentPlayer`**」
的时刻。此时：
- `autoAction` 不认竞价（它只把出局者的回合推走）→ `null`；
- 真人那块竞价屏属于**当前玩家**的回合，不会为出局者出现 → 没人开屏；
- 而 `decideAction` 把竞价那一支放在 `isAiTurn` **之后** → 也返回 `null`。

⇒ 整局**停在 `awaitingDecision`**（实测种子 42 第 1236 回合）。
新增 `state/reduce.ts` 的 `orphanedAuction(state)` 作为这一情形的**唯一判据**：
`decideAction` 与客户端的 `scheduleAi` 都用它 —— 前者只在「当前玩家已出局」时才
接手竞价（真人坐在桌上时照旧让位给屏，`ai/policy.test.ts` 的既有契约不变），
后者据此不再早退。

#### 诚实边界

- **重抽循环加了上限**。原版的「抽到空槽就重抽」是无界的，靠 `cmp esi,3 / jle`
  保证至少还剩一个非空槽。复刻给它加了一道**上限**（一个非空槽都没有就收手）——
  死循环比少拍一场更糟。在能走到的那条路上上限永不触发，抽签次数与原版逐次相同。
- **`0x43bde5` 的第三参（`arg3`）是纯表现**：`0x43c6c0`/`0x43c6f0` 只在它非 0 时
  `call 0x4549cf(5)` 弹提示、`call 0x454bcc` 收提示。故新闻 7（`arg3=1`）与
  破产（`arg3=0`）在 core 里走同一条开拍路径，复刻不实现横幅。
- **`0x40d143` 起的持股清算**只做了「非空仓才卖」，而 `0x40a4e1`（小地图/信息窗刷新）
  与 `0x4549cf(5)` 这类调用属表现层，未复刻。
- **`0x43243f` 的 `xor eax, esi`** 在魔法屋那一段里看着是死代码（`mov ax, ...`
  立刻把低 16 位覆盖掉，而 `esi ≤ 3`）。按「取节点号」理解实现 ——
  该疑点规格里也已登记（`magic-house.md` §未决第 6 条），未在本轮解决。
- **客户端只改了 `scheduleAi` 的一道闸门**；「出局者的拍卖要不要开竞价屏」
  属表现层，未动 —— core 现在保证的是：无论谁驱动，竞价都答得掉、答不完不丢场次。
- **★★ 顺手撞见、本轮未处理（簇 C，优先级很高）**：**开一场拍卖会推进原版的全局随机流，
  复刻不会。** 原版算各家心理价位的那支 `0x439f0d` **调用 `rand()`**
  （`gen/db.txt` 的调用表：`0x439f0d` → `callees` 含 `0x456f2d`）；
  复刻的 `state/reduce.ts` `openAuction` 却用
  `seed = (state.rngState ^ imul(entityId+1, 0x9e3779b1))` **派生**一个种子交给
  `auctionAiLimits`，**不消耗也不回写 `rngState`**。
  ⇒ 每开一场拍卖，复刻的全局随机序列就与原版错位一次，之后所有随机事件
  （命運/新聞/骰子/魔法屋）都对不上。这是第 37/38 条那类「多掷/少掷一次」的**同一类**
  缺陷，只是位置在拍卖里；`拍賣卡` / `新聞 7` / `魔法屋` 三条路**同等受影响**，
  本轮新加的下線拍卖亦然。修它要先把 `0x439f0d` 里 `rand()` 的**次数与顺序**
  （每家几次、是否含 `0x43be74` 的取整那一步）逐条数清，再让 `openAuction` 回写 `rngState`。
  **✅ 已完成（第 45 条，见 §7.27）：改回消费全局流，每家电脑 2 次并回写 `rngState`。**
- **顺手撞见、本轮未处理**：`state/types.ts` 里 `pendingNpcSlots` 的注释写着
  「不进 `stateFingerprint`？—— 不，**要进**」，但 `net/protocol.ts` 的
  `stateFingerprint` 的显式字段表里**没有** `pendingNpcSlots`，也没有 `pending`
  （新加的 `pendingQueue` 同理不在）。这是**注释与实现对不上**，不是本轮引入的。
  两边谁对需要一次判断：若「待决交互/惡人段游标」属于必须被校验和抓到的规则分歧，
  就该进指纹（联机地基，见簇 C）。列进 §7.3 待办。
