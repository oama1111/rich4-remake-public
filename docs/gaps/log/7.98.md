### 7.98 ★★★ 第 115 条（本轮）：把「整屏计时」那条**待验证**查到根 —— `[0x46cad8]` 不是 tick 计数而是**模态深度**；并解出 `0x450f04`（一帧重绘 = 一帧动画）

第 114 条登记了一条「待验证」：本引擎整屏演出用 `performance.now()`，
原版用 `SetTimer` + 窗口消息，**非默认速度档下会不会走样**。
本轮把它查到根，结论分两半 —— 一半是**虚惊**，一半是**真差异**。

#### (1) `[0x46cad8]` 的真身：**模态对话框的嵌套深度**

投注屏建屏时 `SetTimer(hwnd, [0x46cad8], 0x64, 0)`（`0x0042f8b0`），
而 `WM_TIMER` 分支要求 `wParam == [0x46cad8]`（`0x0042fa49`）。
原先按「定时器 id = 当时的 tick 计数」读 —— 那个读法推出「计数器一直在涨、
所以这条定时器最多只响一次」，但**推不出它是什么**。本轮查到：

```asm
; @source 0x004018e7 —— 开一扇**模态窗口**
004018eb  edx = [0x46cad8] / inc edx / mov [0x46cad8], edx   ; ★ 深度 +1
004018fe  mov [eax*4 + 0x48a010], <模态过程>                  ; 过程指针入栈表
00401918  call PostMessageA(hwnd, 0x401, …)                    ; 投 0x401 去建窗
00401957  dec dword [0x46cad8]                                 ; ★ 收窗时深度 −1
; @source 0x00401982 / 0x0040199e 是同一件的另一支（过程 = 0x417e26）
```

⇒ **`[0x46cad8]` = 模态深度**（`0x401` 见 `0x402`，见 `0x401966`），
`0x48a010` 是一张「深度 → 模态过程」的表。于是投注屏那道闸的真实语义是：

> **「这扇窗还在最上层时，才推进它的动画」** —— 一旦有模态窗口压在它上面
> （深度变了），投注屏的 `WM_TIMER` 就被忽略。这是原版**暂停被盖住的窗**的手法，
> **不是**「每 N 个 tick 推进一次」。

★ 这一点很重要：它把「定时器只响一次」这个怪现象解释成了**有意行为**，
而不是原版的 bug。复刻侧对应的是 `UiScreen.active()` 的「只 tick 接管整屏的那一屏」
（`main.ts` 的 `overlay.tick?.(uiEnv())`）——**语义等价**。

#### (2) 真差异：受「游戏速度档」分频的是**渲染循环**，不是定时器

```asm
; @source 0x00401fad（每帧重绘里）
00401faf  al = [0x497158]                  ; ★ cfg[0] = game speed
00401fb4  al = [eax + 0x46cb20]            ; ★ 分频表 = [6,4,2,0]（实测 6/4/2/1）
00401fbf  edx = [0x46cb23] / inc / mov [0x46cb23], edx
00401fcc  cmp eax, edx / jg 0x401fdd
00401fd0  mov [0x46cb23], ebx
00401fd6  mov byte [0x46cafa], 1           ; ★ 本帧该走一次游戏 tick
```

⇒ 速度档分频的是**游戏 tick**（`[0x46cafa]` → 主循环 `call 0x40d7c4`），
而**每帧重绘**（以及挂在它上面的各屏动画）始终按渲染帧率走。

#### (3) ★★ 顺带解出 `0x450f04`：**一帧重绘 = 一帧动画**

投注屏每帧重绘的尾巴上有一句 `0x0042fd5f call 0x450f04`。这个函数原先
只被记成「输入轮询还是动画推进」未决（`small-games.md` 第 7 条）。本轮读通：

```asm
; @source 0x00450ff2
00450ff2  lea eax, [ebx + ebp]      ; ebp = 当前块长度 ⇒ 游标前移
00450ff5  mov [0x476378], eax       ; 全局动画游标
00450ffa  cmp word [ebx+4], 0xf1fa / jne 0x450fea   ; 找下一个 FLIC 帧头
```

⇒ 它每次调用**恰好推进一帧**（走完当前帧的块链就停），所以
**一帧重绘 = 一帧动画**、**不看速度档**。这同时把复刻侧那条「`LOT_BONUS_MS = 71`
是假设」的注释升级成**已解**（71 ms 是当年那台机器的实际帧时）。

#### (4) 结论：待验证项**收窄成一条**

| 项 | 结论 |
|---|---|
| 定时器闸门（`wParam == [0x46cad8]`）| ✅ 语义 = 「窗还在最上层才推进」，与复刻的「只 tick 活动屏」**等价** |
| 跑馬燈 FLIC 的推进节奏 | ✅ 一帧重绘一帧，**不看速度档**；复刻的 71 ms 观感成立 |
| **各屏的「毫秒常量」** | ⚠️ **真差异保留**：原版受速度档分频的是游戏 tick，而这些屏的动画按渲染帧率走 —— 复刻用毫秒常量表达「多少渲染帧之后换下一拍」时，**只有默认速度（`speed=1`）能对上**（常数当初就是按 1 tick = 80 ms 反推的）。非默认速度下节奏会偏。 |

⇒ 因此第 114 条那条偏离**不是**「定时器间隔会变」，而是
**「复刻把『渲染帧数』写成了固定毫秒」**；修法是把这些常量换算成
「渲染帧数 × 每帧毫秒」，或让 `UiScreenEnv` 暴露帧率/档位。
登记在 `known-deviations.md`（本轮已改写那一条的措辞与结论）。

#### (6) ★ 补一条**资产级**证据：`71 ms` 就是 FLIC 头里写的帧时

`Data.mkf` 资源 14/16/17（投注屏那三段跑馬燈/影片）**不是 FLIC**（各 80,000 B
的无头位图），而资源 **416**（冠军奖座那一段）实测是 FLIC：

```
res 416: frames=10 frameMs=71 100x100     ← 直接从 MKF 头解析（parseFlicInfo）
```

⇒ `lottery-screen.ts` 里那个 `LOT_BONUS_MS = 71` **与资产头一致**，
不是拍脑袋的常数；而投注屏的**表情动画**（眨眼/换嘴）按 `0x113` 那 100 ms 定时器
推进，对应复刻的 `LOT_TICK_MS = 100` —— 两者**都对**。
（本轮的教训：把「每帧重绘调一次 `0x450f04`」直接读成「50 fps 播片」是**过度推断**；
真正的帧时在**资产头**里，`frameMs` 字段才是权威。）
