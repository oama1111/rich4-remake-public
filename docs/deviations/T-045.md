## D-045-1（有意偏离）左列那 8 行的格图（资源 0 图 6 / 图 7）**没画**

@source `loc_0044e2f0`（常态）与 `loc_0044e33c`（选中）：

```asm
0044e2f0  mov eax, [0x4761a8]        ; 小分项表的第 8 项指针
          lea eax, [eax + 0xc]       ; + 0xc → 图 6
          push y / push x / push eax / push surface
          call fcn_004563f5          ; 贴图
```

**现象**：把资源 0 的图 6 / 图 7 解出来（`assets-clean/help/0000_006.png`、
`0000_007.png`）看，它们是**珊瑚底 + 一个三角**的小钮（图 6 = 右向三角、
图 7 = 下向三角），尺寸 20×18 / 18×14；把它们贴到左列 `(26, 38 + 21i)`
会**盖掉那条绿带**（浏览器里目视核对过：左列变成一串珊瑚色小方块，
与实机截图 / 底图完全不像）。

**为什么会这样**：`0x4761b4` 每项的第 3 个 dword（+0x08）**不是图号**，是**起始
资源号**（1 / 2 / 8 / 20 / 23 / 39 / 57 / 87，单测钉住；章↔资源的完整区间见
D-045-2）。原版这一屏的左列那 8 行的
分隔线本来就**烘在底图**（图 0）里 —— 左列有 8 条暗绿横线。

**处置**：**不画图 6 / 7**，左列只画章名（15 号白字带黑描边）。
单测里保留了 `chipImage(i, hot) === 6 / 7` 这条事实（图号本身没错），
只是绘制那一步不用它。**这是本卡唯一一处「故意和原版不一样」**。

> 反过来说：若中央认为该画，那要先把「图 6 / 7 到底是左列格还是中部三角」
> 这条查清 —— 本模块量到的另几张（图 4 / 5 / 8..11）与 6 / 7 是同一族
> 「珊瑚底三角」，四张 22×18 / 22×15 / 20×18 / 18×14 依次是
> **上 / 下 / 右 / 左**四个方向，正合中部那两颗钮（原版这一屏只用到上、下）。

## D-045-2（字段读法已订正 · 章↔资源映射已修）剩下的唯一开放问题：滚动单位

> 本节原来的结论（「条目表第 4 个字段是 `maxScroll`，与解出的行数对不上，
> 需中央复核」）**已作废**：那是把条目表 5 个 dword 的后两个读反了。
> 下面记订正后的字段真义、已修的章↔资源映射，以及唯一还没定的那条。

### 一、字段读法（已订正）@source VA `0x4761b4`，20 字节/项 × 8 项

| 偏移 | 含义 | 0..7 的值 |
|---|---|---|
| +0x00 | 章名串指针（串表 `0x466052` 起，每串 9 字节） | 操作說明 / 遊戲畫面 / … |
| +0x04 | 另一个指针（未解，本模块不用） | — |
| +0x08 | **起始资源号** | 1, 2, 8, 20, 23, 39, 57, 87 |
| +0x0C | **该章占几个资源** | 1, 6, 12, 3, 16, 18, 30, 13 |
| +0x10 | **当前滚动位置**（运行时会写它） | 全 0 |

权威 dump（自己复跑核对）：

```bash
python3 - <<'EOF'
import importlib.util, struct
spec=importlib.util.spec_from_file_location('d','tools/disasm.py'); m=importlib.util.module_from_spec(spec)
try: spec.loader.exec_module(m)
except SystemExit: pass
exe=open('../Rich4/rich4.exe','rb').read(); off=m.va_to_off(0x4761b4)
for i in range(8):
    t,f1,start,cnt,scroll = struct.unpack_from('<5I', exe, off+i*20)
    o=m.va_to_off(t); e=exe.index(b'\x00',o)
    print(i, exe[o:e].decode('cp950'), 'start',start,'count',cnt,'scroll',scroll)
EOF
```

1. **+0x0C 是「该章占几个资源」，不是 `maxScroll`。** 证据：8 组区间首尾相接
   （`1 → 2 → 8 → 20 → 23 → 39 → 57 → 87 → 100`），第 7 章收在资源 99
   （`87 + 13 − 1`），与 `help.mkf` 的资源区间严丝合缝；取正文那条
   `read_mkf(help, entry.res + scroll, 0, &size)` @0x44e179 正是按资源号走的。
   旧版把它当 `maxScroll`（读出 0 / 22 / 0 / 12 / 1 / 0 / 739 / 95），语意不通。
2. **+0x10 是「滚动位置」，不是「左列格高 `h`」。** 下滚 @0x44e944 与上滚
   @0x44e881 都直接 `add / sub` 这个 dword（exe 初值全 0）。旧版
   `HELP_CHAPTERS[i].h` 是把它误读出来的，绘制里也没用到，已删。

### 二、章 ↔ 资源映射（已修）

旧版按「一章一资源」硬编码 `res = 1, 2, 3, 4, 5, 6, 7, 88`，于是第 2..7 章
显示的都是**别的章**的文字（实测：第 2 章显示资源 3 的「土地：個人擁有土地的」、
第 6 章显示资源 7 的「現金：購買土地、支付」、第 7 章从资源 88 起）。
现按 exe 的 8 组区间重建：

| i | 章 | 资源区间 | 行数 | maxScroll（本模块口径） |
|---|---|---|---|---|
| 0 | 操作說明 | 1..1 | 4 | 0 |
| 1 | 遊戲畫面 | 2..7 | 104 | 96 |
| 2 | 遊戲指令 | 8..19 | 102 | 94 |
| 3 | 房 地 產 | 20..22 | 190 | 182 |
| 4 | 特殊地點 | 23..38 | 79 | 71 |
| 5 | 特殊人物 | 39..56 | 112 | 104 |
| 6 | 卡  片 | 57..86 | 338 | 330 |
| 7 | 道  具 | 87..99 | 148 | 140 |

正文**不再手抄**：由 `tools/gen-help-lines.py` 从 `../extracted/help/NNNN.bin`
（CP950，NUL 分隔的行）生成 —— 不带参数 = 只校对（不一致退 1），`--write` =
就地改写 `help-screen.ts` 里 `HELP_CHAPTERS` 与 `HELP_LINES_0..7` 两段标记区。
单测逐章钉住首行 / 末行 / 行数（行数从资源文件现算），并有一条反向断言：
把第 2 章换回资源 3 的文本时必红（探针核过，7 条一起红）。

### 三、剩下的唯一开放问题：滚动单位是**资源**还是**行**

exe @0x44e944 的下滚夹取是 `max = [entry+0x0C] − 8`，而 `[entry+0x0C]` 是
**资源数**；滚动量 `[0x47601c]` 被**加到资源号上**再 `read_mkf` @0x44e179，
每次只读**一个**资源，再把该资源缓冲按 NUL 切行、画到下一个 `@` 或画满 14 行
（`cmp ebx, 0xd` @0x44e1be）。也就是说：原版的滚动单位像是**资源**，一屏画的
是一个资源的正文（不是 8 行）。

本模块的 `scroll` 是**行**偏移（一屏 8 行、上/下滚步长 8 行），
`maxScroll = max(0, 行数 − 8)`。两者只有在「滚动单位 = 资源」时才等价。
需要中央定案的只有这一条：

- 若原版确实「一屏一资源、上/下滚各跳 8 个资源」，本模块要把 `scroll` 改成
  资源号（`read_mkf(help, res + scroll)`），夹取改成 `max(0, resCount − 8)`；
- 若下滚箭头是逐屏滚，则现口径（行 − 8）成立。

**判据缺口（登记）**：`fcn_0044dfb4` 只读资源 0，asm 里正文文本的取用
**只有 0x44e179 这一处 `read_mkf`**，没找到第二条取正文的路 —— 所以
「一屏 = 一个资源 / 每次跳 8 个资源」那句还差一张实机截图（卡片章按一下下滚，
看是跳 8 个资源还是跳一屏）才能闭环。在此之前**不猜着改**。

## D-045-3（有意照抄）上／下滚三角的**画**与**命中**错位

- **画**：@source `0x44e11f` / `0x44e14e` —— `(170, 43)` / `(170, 59)`，在**中列**。
- **命中**：@source `0x476254` 的第 5 / 6 项 —— `x ∈ [322,345]` / `[343,366]`，
  在**右列**。

两者对不上（原版自己如此）。本模块**照抄**：框按表、画按常量，不去「修正」。
所以点那两颗钮要按**右列**那一带（x 322..366、y 48..80）才中，
点画面上看见的三角（x 170..192）不中。若实机截图显示原版点三角是中的，
说明这两条里有一条读反了，请中央仲裁。

## A-045-3（事实核对 · 卡片描述已订正）「三颗钮」其实是三组、共六条命中

工具列 #1 打开的这一屏**没有「关闭」钮** —— 关屏只有右键 / 熱鍵 / 点面板外
三条路（`loc_0044e546`）。原版的三组钮是：

| 组 | 干什么 | 命中项 |
|---|---|---|
| 0 | 左列八行选章 | 0 / 1 |
| 1 | 上一章 / 下一章 | 2 / 3 |
| 2 | 上滚 / 下滚（一屏 8 行） | 4 / 5 |

本模块按这个实现了 `hitHelp` / `applyHelpHit`，`helpScreen.hotkey(HOTKEY.help)`
开关屏（`HOTKEY.help = 24`，`hotkeys.ts` 的 `help`）。

## D-045-4（需中央复核）右列几处落点**互相打架**，本模块照抄原值

下面四个 x 都是从 exe 里直接读出来的，但它们指向的**列**并不一致
（底图那三列实测：绿 24..90、珊瑚 106..196、黄 210..370）：

| 画什么 | 局部 x | 落在哪 | @source |
|---|---|---|---|
| 章名条（图 2，珊瑚条） | **26** | 珊瑚列 | 0x44e056 |
| 左列八行章名（选中 / 其余） | 26 / **59** | 珊瑚列 / 珊瑚列 | 0x44e08c / 0x44e092 |
| 右列分项标题 | **140** | 珊瑚列 | 0x44e0c8 |
| 正文八行 | **232** | 珊瑚列与黄列之间 | 0x44e1d1 |
| 上／下滚三角 | 170 | 珊瑚列 | 0x44e11f / 0x44e14e |
| 上／下滚**命中框** | 322 / 343 | 黄列 | 0x476254 |

也就是说：**只有「正文 232」落在黄列附近，其余「右列」的东西都落在珊瑚列**
（而珊瑚列中间已经有两颗三角与一条章名条）。本模块**一律照抄 exe 的常量**
（不按「看起来该在哪列」挪），因此实机上这几个元素会挤在珊瑚列里。
若实机截图显示它们确实在黄列，那说明面板的屏幕落点不是 `(20,60)`
或底图不是整张 400×400 铺满 —— 这两条本模块都是从 exe 常量直接读的
（`0x417d9f` / `0x417da1`），请中央以实机截图仲裁后再动。
